반려견을 맡길 수 있는 애견 유치원·호텔을 지도 기반으로 탐색하고 예약할 수 있는 iOS 플랫폼.  
공공데이터를 출발점으로 서울 지역 업체를 큐레이션하고, 승인된 파트너에 보호자 리뷰·채팅·예약 기능을 제공한다.

**기간:** 2026년 6월 ~

**스택:** Swift, SwiftUI, Observation, KakaoMapsSDK, TypeScript, Hono, Cloudflare Workers, D1, R2, Durable Objects

### 1. 공공데이터 좌표계 변환

**문제**
data.go.kr 동물위탁관리업 API가 반환하는 좌표가 WGS84(GPS)가 아닌 EPSG:5181(중부원점 TM) 좌표계라 카카오 지도에 그대로 꽂으면 핀이 엉뚱한 곳에 찍혔다.

**고민**  
외부 라이브러리를 쓰면 간단하지만, iOS 앱에 좌표 변환 라이브러리를 CocoaPods로 추가하면 의존성이 늘어난다. 변환 공식 자체는 수학 연산이라 직접 구현이 가능한 수준이었다.

**해결**  
GRS80 타원체 기반 TM→WGS84 역변환을 `TMConverter` enum으로 직접 구현했다. 변환 후 대한민국 영역(위도 33~39, 경도 124~132)을 벗어나는 좌표는 필터링해 잘못된 핀을 차단했다.

```swift
let coord = TMConverter.toWGS84(x: x, y: y)
guard coord.lat > 33, coord.lat < 39, coord.lon > 124, coord.lon < 132 else { return nil }
```

**이 방법을 선택한 이유**  
외부 의존성 없이 단일 파일(AnimalBoardingService.swift)에서 처리 가능하고, 변환 로직을 작은 함수로 분리해 검토할 수 있고 새 라이브러리를 추가하지 않아도 된다. 다만 공식을 사용했다는 사실만으로 구현 정확도까지 보장되는 것은 아니므로, 좌표 범위 검사와 주소·지도상 위치 대조를 함께 고려했다.

### 2. API 키 보안 — 클라이언트 설정 분리에서 서버 Secret으로

**문제**  
초기 구현은 외부 API 자격 증명을 iOS 설정에서 직접 사용하는 구조였다. 소스 저장소에서 값을 분리하더라도 빌드된 앱 번들에서는 서버용 키를 추출할 수 있어 무단 사용과 쿼터 소진 위험이 남았다.

**고민**  
대안으로 `.env` 파일, 별도 plist, 빌드 스크립트 등이 있었다. 개발·테스트에서 주입하는 환경변수와 배포 앱의 설정은 구분해야 했다. 서버처럼 `.env`가 자동으로 로드되는 구조가 아니고, 값을 앱에 포함하는 방식으로는 Secret 노출 문제를 해결할 수 없었다.

**해결**  
1차로 Xcode의 **xcconfig(Configuration Settings File)** 방식으로 로컬 설정과 저장소를 분리했다.

- 클라이언트에서 사용하도록 설계된 앱 식별자만 `Secret.xcconfig`에 보관 → `.gitignore`로 Git 제외
- `Info.plist`에는 변수 참조만 남김: `$(KAKAO_NATIVE_APP_KEY)`
- 빌드 시 Xcode가 xcconfig를 읽어 값을 자동 주입

```
// Secret.xcconfig (git 제외)
KAKAO_NATIVE_APP_KEY = <로컬 설정값>

// Info.plist (git 포함)
<key>KAKAO_NATIVE_APP_KEY</key>
<string>$(KAKAO_NATIVE_APP_KEY)</string>
```

이후 보안 경계를 다시 검토해 네이버 Client Secret·Kakao REST Key·공공데이터 Service Key처럼 서버에서만 써야 하는 값은 Cloudflare Worker Secret으로 옮겼다. 앱은 제한된 Worker API만 호출하며 Release 검사에서 금지된 서버용 키 이름과 값이 번들에 포함되지 않는지 확인한다.

**이 방법을 선택한 이유**  
클라이언트용 공개 식별자는 Xcode 네이티브 설정으로 환경별 주입하고, 서버용 비밀은 신뢰 경계 밖인 Worker에 둬야 두 노출 경로를 모두 막을 수 있다. 이 과정을 통해 “Git에서 제외됨”과 “배포 앱에서 비밀임”은 서로 다른 문제라는 점을 반영했다.

| 방법 | 장점 | 단점 |
|---|---|---|
| **xcconfig** | 클라이언트 설정의 저장소 분리, Xcode 네이티브 | 앱 번들에 들어가는 서버용 Secret은 보호하지 못함 |
| **Worker Secret (서버용 값에 채택)** | 앱 번들에서 서버용 자격 증명 제거 | 서버 프록시·캐시·남용 방지 필요 |
| 환경변수 | 개발·테스트 주입이 간단 | 배포 앱에 포함할 서버 Secret의 보호 수단이 되지는 않음 |
| 별도 plist 파일 | 직관적 | 결국 파일 자체를 gitignore 해야 해 xcconfig와 동일 |
| 소스·앱에 서버 키 포함 | 구현이 단순함 | 저장소·앱 번들 노출과 키 교체 위험 |

### 3. Pods git 추적 문제

**문제**  
`.gitignore`가 없어서 CocoaPods의 `Pods/` 디렉토리(279개 파일)가 git에 추적되고 있었다.

**고민**  
이미 git이 추적 중인 파일은 `.gitignore`를 추가해도 자동으로 무시되지 않는다는 점을 인지해야 했다.

**해결**  
`.gitignore` 생성 후 `git rm -r --cached Pods/`로 추적 목록에서만 제거했다. 실제 파일은 삭제되지 않고 git이 더 이상 관리하지 않는다.

**이 방법을 선택한 이유**  
iOS 생태계 표준 관례다. `Podfile.lock`만 커밋하면 누구든 `pod install` 한 번으로 동일한 버전을 재현할 수 있다.

### 4. 하드코딩 사용자 정보 제거 — UserProfile 모델

**문제**  
`BookingView`의 보호자 이름·연락처·주소, `HomeView`의 인사말이 문자열로 박혀 있었다.

```swift
formField(label: "이름", value: "김상민")   // 하드코딩
Text("상민님")                               // 하드코딩
```

**고민**  
Core Data나 Keychain을 쓰면 과하다. 간단한 사용자 설정값이라 UserDefaults로 충분하다고 판단했다.

**해결**  
`@Observable` 기반 `UserProfile` 모델을 만들어 `UserDefaults`에 영속 저장하고 `RootView`에서 환경 객체로 주입했다.

```swift
@Observable
final class UserProfile {
    var name: String {
        didSet { UserDefaults.standard.set(name, forKey: "profile_name") }
    }
    // ...
}
```

뷰에서는 `@Environment(UserProfile.self)`로 읽어 사용한다.

이것은 초기의 로컬 저장 구현이다. 이후 다른 기기에서 프로필이 복원되지 않는 문제를 확인하면서 서버를 기준으로 동기화하도록 확장했다. 현재의 계정별 복원과 늦은 조회 방지는 §17에 따로 정리했다.

**이 방법을 선택한 이유**  
Swift Observation 프레임워크를 사용해 `@Observable`로 선언하면 변경 시 관련 뷰가 자동으로 업데이트된다. `didSet`으로 UserDefaults에 즉시 저장해 앱 재시작 후에도 값이 유지된다.

### 5. TypeScript any 타입 제거

**문제**  
Cloudflare Workers 백엔드의 모든 요청 바디가 `any` 타입으로 처리되고 있어 TypeScript를 쓰는 의미가 없었다.

**해결**  
라우트별 요청 바디 타입을 명시적으로 정의했다.

```typescript
type ReservationBody = {
  user_id?: number; userId?: number
  start_date?: string; startDate?: string
  // ...
}

const body = await c.req.json<ReservationBody>()  // any → 명시적 타입
```

**이 방법을 선택한 이유**  
iOS 클라이언트에서 snake_case와 camelCase를 혼용해 보내는 구조가 이미 있었기 때문에 두 형태 모두 optional로 받는 타입을 정의했다. 잘못된 구조의 요청이 들어오면 개발 중에 타입 오류로 바로 잡을 수 있다.

### 6. 예약과 채팅방의 도메인 설계 — 공공 가게의 ID 부재 문제

**문제**  
예약(`reservations`)은 `store_id`가 필수인데, 지도의 가게는 공공데이터 API에서 오기 때문에 우리 DB에 `store_id`가 없다(이름·주소만 존재). 또 예약할 때마다 채팅방을 새로 만들면, 같은 가게에 두 번 예약한 사용자가 서로 다른 방을 갖게 되어 대화가 흩어진다.

**고민**  
- **가게 식별**: (A) 예약마다 임시 번호 부여 — 같은 가게를 못 묶음. (B) 이름만 저장 — 구조적 식별 불가. (C) 공공 가게를 우리 `stores`에 등록해 안정적 번호 부여.
- **채팅방 범위**: 방을 '예약'에 묶을지, '가게'에 묶을지, '(사용자+가게)'에 묶을지. 다중 사용자를 고려하면 (사용자+가게)라야 남의 대화가 섞이지 않는다.

**해결**  
- 리뷰 기능에서 이미 쓰던 `store_key`("이름\|주소") 방식을 재사용. 예약 시 `store_key`로 `stores`를 조회해 **있으면 재사용, 없으면 등록(자동 증가 번호)** → 같은 가게는 항상 같은 `store_id`.
- 채팅방은 `chat_rooms(user_id, store_id UNIQUE)` 테이블로 **(사용자+가게) 조합당 1개**. 예약 시 해당 방을 조회/생성하고 그 방에 '예약 요청 완료' 메시지를 남긴다.
- API가 `{reservation_id, room_id}`를 함께 반환해 클라이언트가 이후 채팅방으로 바로 연결할 수 있게 했다.

```typescript
// 같은 가게는 같은 번호, 같은 (유저·가게)는 같은 방
const storeId = existing ? existing.store_id : (await insertStore(...)).id
const roomId  = room     ? room.room_id     : (await insertRoom(userId, storeId)).id
```

**이 방법을 선택한 이유**  
공공 API 데이터를 우리 도메인으로 끌어올 때 흔한 "외부 식별자 ↔ 내부 식별자" 매핑 문제다. `store_key` upsert로 외부 데이터를 자연스럽게 내부 엔티티로 승격시키고, 리뷰와 동일한 키를 써서 일관성을 유지했다. (사용자+가게) 방 설계는 카카오톡 채널 방식과 동일해 사용자에게 직관적이다.

### 7. 첫 화면이 첫 탭에 반응하지 않던 버그 — SwiftUI AttributeGraph 순환

가장 오래 붙잡았던 버그이자, SwiftUI 내부 동작을 깊이 이해하게 된 사례다.

**문제 (증상)**
앱을 새로 설치하고 **처음 켠 시작 화면**에서 역할 선택 카드(보호자 / 보호자·사장님)를 탭하면, 체크 표시도 테두리 색도 전혀 바뀌지 않았다. 그런데 한 번 로그인했다가 **로그아웃해서 다시 나타난 "똑같은" 시작 화면**에서는 멀쩡히 동작했다. 즉 **"콜드 런치 직후 첫 진입"에서만** 나타나는 비대칭 버그였다.

**왜 어려웠나**
탭 자체는 정상이었다. 로그를 심어 보니 탭할 때마다 상태값(`selectedRole`)은 `.owner`로 잘 바뀌었고, 그 상태로 로그인하면 실제로 사장님 계정으로 로그인까지 됐다. **상태는 바뀌는데 화면(`body`)만 그 변화를 다시 그리지 않는** 기묘한 상황이었다. 처음에는 표면적인 원인들 — 뷰 전환 애니메이션, 버튼 스타일, 상태를 저장하는 위치, 빌드 캐시 — 을 하나씩 의심하고 수정했지만 전부 빗나갔다.

**체계적 진단**
추측을 멈추고 사실을 좁혀 나갔다.

1. `body` 진입점에 로그를 심어, 탭 후 **`body`가 재평가 자체를 안 한다**는 것을 확정했다. (렌더링만 얼어붙은 게 아니라 아예 다시 계산되지 않았다.)
2. 시뮬레이터를 명령줄에서 직접 실행해(`xcrun simctl launch --console-pty`) 콘솔을 캡처했더니 결정적 로그가 나왔다:

```
=== AttributeGraph: cycle detected through attribute 5436 ===
```

**근본 원인**
SwiftUI는 뷰의 의존 관계를 **AttributeGraph**라는 방향 그래프로 관리하고, 어떤 값이 바뀌면 그 그래프를 따라 영향받는 뷰를 다시 그린다. 이 그래프에 **순환(cycle)** 이 생기면 SwiftUI는 무한 루프를 막기 위해 **그 경로의 갱신 전파를 끊어버린다.** 그 결과가 바로 "처음 한 번만 그려지고 이후로는 어떤 상태 변화에도 얼어붙는" 화면이었다.

순환의 근원은 시작 화면의 상단 여백 코드였다:

```swift
.padding(.top, UIApplication.safeAreaTop + 12)   // safeAreaTop이 UIKit 윈도우의 safeAreaInsets를 읽음
```

`safeAreaTop`은 UIKit 윈도우의 `safeAreaInsets`를 **`body` 평가 도중에** 읽는다. 그런데 콜드 런치 순간엔 윈도우 레이아웃(safe area)이 아직 확정되기 전이라, 다음과 같은 순환이 만들어진다:

```
화면 콘텐츠 크기  →(의존)  body 평가  →(읽음)  safe area  →(의존)  윈도우 레이아웃  →(의존)  콘텐츠 크기 …
```

로그아웃 후 재진입 때는 윈도우가 이미 자리를 잡아 safe area가 확정돼 있으므로 순환이 생기지 않는다 — 이것이 "콜드 런치에서만 실패하는" 비대칭의 정체였다.

**해결 (가장 효과적이었던 방법)**
핵심은 **`body` 평가 중에 UIKit 레이아웃 값을 읽지 않는 것**이다. safe area 값을 `@State`에 캐시하고, 레이아웃이 끝난 뒤 실행되는 `onAppear`에서 실제 값을 채워 넣도록 바꿨다. `body`는 이 `@State` 값만 읽으므로 UIKit 레이아웃과의 의존 고리가 끊어져 순환이 사라진다.

```swift
private struct SafeAreaTopPadding: ViewModifier {
    @State private var topInset: CGFloat = 56          // 기본 safe area(44) + 12
    func body(content: Content) -> some View {
        content
            .padding(.top, topInset)                    // body는 캐시된 @State만 읽음 (순환 없음)
            .onAppear { topInset = UIApplication.safeAreaTop + 12 }  // 레이아웃 확정 후 실제 값 주입
    }
}
```

처음에는 시작 화면에만 인라인으로 적용해 원인을 검증했고, **같은 위험 패턴이 다른 11개 화면에도 있었기 때문에** 재사용 `ViewModifier`(`.safeAreaTopPadding()`)로 묶어 `SafeAreaKey.swift` 한 곳에서 관리하도록 정리했다. 이제 `body`에서 safe area를 직접 읽는 곳은 0곳이다.

**검증**
수정 전/후를 콘솔 캡처로 비교했다.

| | 순환 감지 | 탭 후 body 재평가 |
|---|---|---|
| 수정 전 | **1건** | ❌ 안 됨 (화면 얼어붙음) |
| 수정 후 | **0건** | ✅ 됨 (`topInset` 56→59로 갱신되는 로그 확인) |

**이 방법을 선택한 이유**
다른 선택지도 검토했다.

| 방법 | 문제점 |
|---|---|
| RootView의 `.ignoresSafeArea()`를 걷어내고 SwiftUI 기본 safe area 사용 | 12개 화면의 레이아웃을 전부 바꿔야 해 범위·위험이 큼 |
| `GeometryReader`로 safe area 읽기 | RootView가 safe area를 무시하는 구조라 0을 반환 → 사용 불가 |
| **`@State` 캐시 + `onAppear` (채택)** | 기존 레이아웃·아키텍처를 그대로 두고 "`body`에서 UIKit 읽기"만 제거하는 **최소·국소 수정** |

`@State` 캐시 방식은 근본 원인("`body`에서 레이아웃을 읽어 순환이 생김")을 정확히 겨냥하면서 화면 배치나 앱 구조를 전혀 건드리지 않는다. 게다가 `ViewModifier`로 묶어 재발 방지와 코드 중복 제거(DRY)까지 함께 달성했다.

**배운 점**
- **"상태는 바뀌는데 화면이 안 바뀐다"** 는 SwiftUI 특유의 증상은 AttributeGraph 순환을 의심할 강한 신호다.
- `body`는 순수해야 한다. 평가 도중 UIKit 레이아웃처럼 "그 결과가 다시 `body`에 영향을 주는" 값을 읽으면 순환이 생길 수 있다. safe area 같은 값은 캐시하거나 SwiftUI 네이티브 수단으로 받아야 한다.
- UI 자동화 없이도, `body`에 심은 로그 + `simctl` 콘솔 캡처만으로 "추측"이 아닌 "관측"에 근거해 원인을 특정하고 수정을 검증할 수 있었다.

### 8. 사장님↔손님 양방향 채팅 — 역할을 '플래그'에서 '계정'으로

**문제**  
채팅이 사실상 단방향이었다. 손님이 가게에 문의를 보내면 DB에 쌓이기만 할 뿐, 사장님이 그 메시지를 보거나 답장할 방법 자체가 없었다(백엔드에 '가게 주인' 개념이 없음). 더 근본적으로는, 시작 화면에서 고른 역할(보호자/사장님)이 **같은 계정의 플래그**(`isOwner`)일 뿐이어서 두 역할이 같은 `user_id`를 공유했다 — 채팅·찜·예약·최근 본 가게가 전부 섞이고, 사장님으로 보낸 메시지조차 `sender_id`가 같아 손님이 보낸 것처럼(오른쪽 말풍선) 표시됐다.

**고민**  
- **방 구조**: 사장님용 문의방을 따로 만들 것인가? → 만들면 같은 대화가 두 방으로 갈라진다. 기존 "(손님+가게)당 1방" 설계를 지키고 사장님이 **같은 방에 참여**하는 쪽이 맞다.
- **역할 분리 수준**: 플래그를 유지한 채 화면만 사장님 시점으로 바꿔줄 수도 있지만, `sender_id`가 같은 이상 눈속임일 뿐이다. 역할을 **계정 단위로 분리**해야 데이터가 구조적으로 나뉜다.
- **가게 소유 연결**: 지도의 가게는 공공데이터 출신이라 "이 가게 주인이 누구인지"를 서버가 알 방법이 없다. 소유 관계를 어디에, 어떤 UX로 만들 것인가.

**해결**  
1. **방 재사용**: 사장님용 방을 만들지 않고, `stores.owner_id`(마이그레이션)로 가게 소유를 연결한 뒤 `GET /api/owners/:id/chatrooms`로 "내 가게로 온 방 목록"을 조회해 기존 채팅 목록 상단에 '받은 문의' 섹션으로 노출했다. 말풍선이 원래 `sender_id == 내 userId` 기준이었기 때문에, **채팅방 화면은 한 줄도 고치지 않고** 사장님 시점(사장님 오른쪽/손님 왼쪽)이 자동으로 성립했다.
2. **역할의 계정 귀속**: `users.is_owner` 컬럼을 신설해 역할을 **최초 가입 시 카카오 계정에 영구 귀속**시켰다. 같은 계정으로 반대 역할 로그인을 시도하면 서버가 409로 거절하고 앱이 안내 문구를 띄운다. 모든 데이터가 `user_id` 기준이므로 별도 마이그레이션 없이 채팅·찜·예약이 역할별로 자동 분리됐다. 시뮬레이터 개발자 진입도 역할별 계정(`dev-simulator` / `dev-simulator-owner`)으로 나눠, 기기 한 대에서 로그아웃→역할 전환만으로 양쪽을 테스트할 수 있다.
3. **가게 소유 등록**: 마이페이지 '내 가게'에서 상호명으로 공공데이터 업체를 검색해 등록한다(`POST /api/stores/claim` — 리뷰·예약과 동일한 `store_key` upsert 재사용, 남의 가게면 409, 잘못 등록 대비 해제 API 포함). 받은 문의·받은 예약 요청 모두 이 소유 관계로 스코프된다.
4. **실시간감**: 방을 열어둔 동안 3초 폴링으로 상대 메시지를 반영한다. WebSocket(Durable Objects)이 정석이지만, 포트폴리오 범위에서는 "열려 있는 방"에만 도는 폴링이 비용 대비 충분했다.

**이 방법을 선택한 이유**  
핵심은 "새 기능을 위해 새 구조를 만들지 않는다"였다. 방 재사용은 §6의 도메인 설계(조합당 1방)를 지켰고, 가게 등록은 기존 `store_key` upsert 패턴을 그대로 썼으며, 말풍선 시점 분리는 이미 있던 `sender_id` 비교 로직이 계정 분리의 부수 효과로 공짜로 얻어졌다. 역할을 계정으로 승격한 것도 UI 분기 대신 **식별자(user_id) 층위에서 문제를 풀어** 이후 기능들이 자동으로 올바르게 동작하게 한 결정이다.

> **현재 구현과의 구분:** 위 가게 직접 등록 API 설명은 초기 버전의 기록이다. 현재는 신청을 먼저 저장하고 운영자 승인 후 소유 관계를 연결한다. 역할만으로 다른 가게에 접근할 수 없도록 보완한 과정은 §15에 정리했다.

### 9. 백엔드 의존성 취약점 해소 — 고장난 로컬 npm 환경을 sudo 없이 우회

**문제**  
`npm audit`에서 백엔드 의존성 취약점 6건(high 5·low 1)이 보고됐다. 특히 **hono는 배포 번들에 실제로 실리는 유일한 런타임 의존성**인데 path traversal·CORS 와일드카드 반사 등 5건의 권고가 걸려 있었다(나머지 undici·ws·esbuild는 wrangler 개발 도구 체인). 그런데 `npm audit fix`를 실행할 수 없었다 — 과거 `sudo npm install`의 흔적으로 `node_modules`와 `package-lock.json`이 **root 소유**라, 일반 사용자 권한의 npm이 lockfile과 node_modules 어느 쪽에도 쓰지 못하고 EACCES로 실패하는 상태였다.

**고민**  
- **정석은 `sudo chown`**이지만 비밀번호 입력이 필요한 대화형 작업이라, 가능하면 사용자 개입 없이 풀고 싶었다.
- **POSIX 권한의 세부를 이용한 우회**: 파일의 삭제·이름 변경 권한은 파일 자체가 아니라 **부모 디렉터리의 쓰기 권한**을 따른다. 부모(`backend-cloudflare/`)는 내 소유이므로, root 소유 `package-lock.json`도 "읽어서 사본 → 삭제 → 사본 복원" 순서로 소유권을 탈환할 수 있었다.
- 같은 논리로 `node_modules`도 이름을 바꿔 치우려 했지만 **실패** — 디렉터리 이동은 그 디렉터리 내부의 `..` 항목 갱신이 필요해 디렉터리 자체의 쓰기 권한을 요구하고, macOS는 같은 부모 안에서의 rename조차 거부했다. 파일은 되고 디렉터리는 안 되는 비대칭.

**해결**  
`node_modules`를 치울 수 없다면 그 자리에서 고치는 것을 포기하고, **깨끗한 임시 디렉터리에 프로젝트의 매니페스트만 복사해 작업**했다:
1. `package.json` + `package-lock.json`을 임시 디렉터리로 복사 → `npm install`(npm 캐시 일부도 root 소유라 `npm_config_cache`로 캐시 위치까지 우회) → `npm audit fix` → **6건 전부 0건으로**.
2. 결과는 hono 4.6.10→4.12.30, wrangler 4.93.0→4.110.0 — 모두 기존 `^` 범위 내 semver 호환 갱신이라 `package.json`은 그대로이고 **lockfile만 변경**됐다.
3. 검증도 그 자리에서: `src/`와 `wrangler.toml`을 임시 디렉터리로 복사해 갱신된 wrangler로 **직접 배포**했다. 배포 대상은 `wrangler.toml`의 워커 이름으로 결정되므로 저장소 밖에서 실행해도 같은 워커에 반영된다. 배포 성공(cron 트리거 유지 확인) 후 읽기 전용 엔드포인트 3종을 curl로 스모크 테스트했다.
4. 갱신된 `package-lock.json`만 저장소로 복사해 커밋. 저장소의 root 소유 `node_modules`는 건드리지 않았고(git 추적 대상도 아님), 근본 수리는 `sudo chown` 1회로 가능함을 기록해뒀다.

**이 방법을 선택한 이유**  
lockfile 갱신은 그 자체로는 아무것도 바꾸지 않는다 — Cloudflare Workers는 **배포 시점에 로컬 node_modules를 번들**하므로, "새 의존성으로 설치된 환경에서의 재배포"까지가 한 세트여야 hono 갱신이 실제 런타임에 반영된다. 임시 디렉터리 방식은 이 세트를 한곳에서 완결시키면서(설치→audit→배포→검증) 고장난 로컬 환경과 저장소를 전혀 건드리지 않았다. 환경이 깨져 있을 때 "환경부터 고치고 작업"이 아니라 **작업에 필요한 최소 환경을 옆에 새로 만드는** 접근이 개입 범위도, 실패 시 되돌릴 것도 가장 적었다.

### 10. 알림장(diary) 기능 — 새 구조를 만들지 않고 기존 도메인 위에 얹기

**문제**  
사장님이 맡은 강아지가 하루를 어떻게 보냈는지 보호자에게 전하는 '알림장'이 필요했다. 어린이집 알림장처럼 사장님이 글을 남기면 보호자가 읽는 흐름이다. 문제는 이 기록을 **무엇에 귀속시킬지**가 애매하다는 것이었다 — 가게? 예약? 채팅방?

**고민**  
- **귀속 대상**: (A) 가게에 붙이면 여러 예약 건이 한 타임라인에 섞인다. (B) 채팅방에 붙이면 잡담과 기록이 뒤엉킨다. (C) **예약에 붙이면** "이번에 맡긴 그 건"의 기록만 시간순으로 모여, 보호자가 '이번 예약은 어땠지'를 바로 본다.
- **작성/열람 화면**: 사장님(작성)과 보호자(열람)에 별도 화면 두 개를 만들 것인가? 두 화면은 데이터도 레이아웃도 거의 같고 '쓰기 UI 유무'만 다르다.
- **알림 전달**: 사장님이 글을 남긴 걸 보호자가 어떻게 아는가? 새 알림 채널(푸시)을 만들 것인가?

**해결**  
세 고민을 모두 기존 구조 재사용으로 풀었다.
1. **예약 귀속 · 타임라인**: 알림장을 `reservations`에 1:N으로 묶고, 한 예약에 엔트리가 시간순으로 쌓이는 타임라인으로 설계했다(`GET /api/reservations/:id/diaries`). 보호자는 예약 내역 카드의 '알림장 보기'로, 사장님은 홈 FAB → 확정 예약 목록에서 진입한다.
2. **화면 1개, 시점 2개**: `DiaryTimelineView` 하나를 `router.diaryContext.canWrite` 플래그로 공유한다 — 사장님이면 하단 '알림장 쓰기' 바와 각 카드의 수정/삭제 메뉴가 켜지고, 보호자면 읽기 전용이다. §8의 채팅 말풍선과 같은 "같은 화면, 플래그로 시점 분리" 패턴이다.
3. **알림은 채팅 자동 메시지로**: 사장님이 알림장을 **작성**하면(수정·삭제는 제외) 서버가 그 보호자의 채팅방에 자동 메시지(sender 0, '맡겨멍')를 남긴다 — `"${강아지이름}의 새 알림장이 도착했어요\n예약 내역에서 확인해주세요"`. 예약 취소·리뷰 요청 안내에 이미 쓰던 sender 0 패턴을 그대로 재사용했고, 안 읽은 채팅 빨간 점 로직에 자동으로 얹혀 **별도 알림 채널이 필요 없었다**.

강아지 이름을 실제로 보여주려고 예약 조회에 `pets` 조인을 더했다(`LEFT JOIN pets … p.name AS pet_name`) — 값이 없으면 '우리 아이'로 폴백해 화면이 비지 않게 했다.

**사진은 스키마 선행 후 비공개 R2로 완성**
초기에는 R2가 준비되지 않아 `diary_photos` 스키마와 빈 `photos` 계약부터 만들었다. 이후 비공개 R2 버킷을 연결해 알림장당 최대 3장, 장당 1.5MB의 JPEG만 받도록 제한했고, 파일은 R2·소유 관계는 D1에 나눠 저장했다. 공개 객체 URL을 쓰지 않고 사진 조회도 Bearer 인증 API를 통과하게 해 해당 예약의 보호자와 가게 사장님만 볼 수 있게 했다. iOS에서는 `PhotosPicker` 원본을 최대 1600px로 정규화하고, 카드 썸네일과 전체 화면 좌우 넘김을 제공한다.

객체 저장소와 관계형 DB는 트랜잭션을 공유하지 않으므로 `diary_photo_deletion_queue`를 D1에 두었다. 업로드 전에 키를 대기열에 넣고 메타데이터 기록이 성공한 경우에만 제거하며, 삭제는 대기열 등록과 D1 행 삭제를 한 배치로 묶은 뒤 R2를 최대 1,000개씩 비운다. Worker 중단이나 R2 오류가 나도 다음 보유기간 작업에서 재시도돼 화면에서만 사라지고 저장소에 파일이 남는 개인정보 누수를 줄였다.

**이 방법을 선택한 이유**  
새 기능일수록 새 구조를 세우고 싶은 유혹이 크지만, 알림장은 이미 있는 세 축(**예약 귀속 · 역할 플래그 · sender 0 자동 메시지**) 위에 얹는 것으로 충분했다. 덕분에 채팅방 화면과 알림 로직은 한 줄도 건드리지 않았고, 새로 쓴 코드는 '타임라인 뷰 + diary CRUD 라우트'로 국한됐다.

### 11. 이모지를 에셋 이미지로 — 인라인 렌더링의 벽

**문제**  
앱 곳곳(빈 상태 안내, 섹션 제목, 채팅 자동 메시지 등)에 유니코드 이모지(🐾 📅 💬 …)를 그대로 썼다. 이모지는 OS·폰트 버전에 따라 모양이 달라지고 브랜드 톤과도 어긋나, 디자인 통일을 위해 자체 PNG 에셋으로 교체하기로 했다.

**해결(1) — 폴백형 EmojiIcon**  
모든 이모지가 에셋을 가진 건 아니라, "에셋이 있으면 이미지, 없으면 이모지 텍스트"로 자동 폴백하는 `EmojiIcon` 뷰를 만들었다. 이모지 문자열 → 에셋 이름 매핑(`petAssetName`)을 한 곳에 모으고, 프레임 크기를 받아 그린다.

```swift
if let name = emoji.petAssetName {
    Image(name).resizable().scaledToFit().frame(width: size, height: size)
} else {
    Text(emoji).font(.system(size: size))   // 에셋 없으면 이모지 그대로
}
```

**부딪힌 벽 — 흐르는 텍스트 속 이모지는 크기를 못 맞춘다**  
로그인 화면 '따뜻한 손길로…' 옆의 발바닥처럼, 문장 중간에 작은 에셋을 끼워 넣고 싶었다. `Text("…\(Image(asset))")`로 인라인 합성했더니 **이미지가 본문 폰트 크기(~17pt)로 커져** 문구를 압도했고, 그 런에 `.font(.system(size: 12))`를 걸어도 비트맵 이미지는 폰트 크기를 따르지 않아 줄어들지 않았다. 여러 방식으로 시도했지만 인라인 합성된 비트맵은 신뢰성 있게 축소되지 않았다.

**해결(2) — 인라인은 포기하고 규칙을 세움**  
결론은 "에셋 이모지는 **프레임 크기를 가진 독립 요소로만 쓴다**"였다. 문장 중간의 인라인 이모지는 전부 제거하고(로그인 푸터·자동 메시지 발바닥 포함), 크기 제어가 필요한 곳은 `HStack { Text(…); EmojiIcon(…) }`처럼 이미지를 별도 요소로 분리했다. 에셋이 아예 없는 이모지(📭 👤 ✍️ 📝 🙏 등)는 톤이 깨지느니 **텍스트만 남기고 지웠다** — 있는 것만 이미지, 없는 것은 글자, 어중간한 혼용은 없앤다는 규칙.

**배운 점**  
SwiftUI의 `Text` 인라인 이미지는 SF Symbol처럼 **폰트 메트릭을 따르는 벡터**에는 잘 맞지만, 고정 크기 비트맵 PNG에는 맞지 않는다. 아이콘을 문장에 자연스럽게 흘려 넣어야 한다면 PNG가 아니라 SF Symbol이나 폰트 글리프를 썼어야 했다. 크기 제어가 필요한 비트맵은 레이아웃 요소로 분리하는 것이 맞다.

### 12. 마스킹된 주소 정밀화 — 이관된 네이버 API를 추적해 연결하기

**문제**  
공공데이터 동물위탁관리업 API의 주소는 개인정보 보호로 상세 번지가 마스킹되어 온다 — `"서울특별시 양천구 목동중앙남로 **, ***호 (목동)"`. 가게 상세 화면은 카카오 키워드 검색으로 전체 주소를 보강하고 있었지만, 일부 가게는 여전히 마스킹 주소가 그대로 노출됐다.

**원인 조사 — 카카오 하나로는 안 되는 이유**  
앱과 동일한 API 호출을 curl로 재현해 보니(키는 xcconfig에서 셸 변수로만 로드, 값 미출력) 문제 가게들은 **카카오맵에 아예 등록돼 있지 않아** 키워드 검색이 0건이었다. 검색 반경을 늘리는 우회는 더 위험했다 — 이름이 비슷한 **다른 지역 가게**가 잡힌다(실측: 동명 가게가 47km 밖에서 매칭). 좌표→주소 변환 폴백도 써봤지만, 핀 좌표의 지번 주소일 뿐 사업자 등록 주소(도로명 + 층·호)와 달라 "맞지 않는 주소"가 됐다.

**벽 — 네이버 검색 API가 조용히 이사 갔다**  
네이버 플레이스에는 이 가게들이 있어서 네이버 지역 검색 API로 전환하기로 했는데, 발급받은 키가 계속 인증 실패(024)를 냈다. 키 문제로 단정하지 않고 엔드포인트 자체를 의심해 조사한 결과: **developers.naver.com의 검색 API는 신규 제휴를 받지 않고, NCP(네이버클라우드) NAVER API HUB로 이관**된 상태였다. 새 키는 형식부터 다르고(ID ~10자/Secret ~40자), 엔드포인트는 `naverapihub.apigw.ntruss.com/search/v1/local`, 헤더는 `X-NCP-APIGW-API-KEY-ID`/`-KEY`를 쓴다. 다행히 **응답 JSON은 구 API와 동일**해서, 엔드포인트와 헤더만 바꾸면 기존 파싱 코드가 그대로 동작했다 — 지역 검색(`NaverLocalService`)과 블로그 후기(`NaverBlogService`) 둘 다 이 방식으로 연결했다.

**해결(1) — 화면 로직: 네이버 우선 + 좌표 검증**  
가게 상세의 보강 체인을 재구성했다.
1. **주소는 네이버 우선** — 네이버 플레이스의 등록 주소는 `"목동중앙남로 80 동구햇살APT 2차 제1층 제107호"`처럼 층·건물·호까지 담고 있다(카카오 도로명은 번지까지만).
2. **전화·카카오맵 링크는 카카오** — 네이버 지역 검색의 telephone 필드는 항상 비어 오므로(하위호환 잔재) 두 API를 `async let` 병렬 호출해 역할을 나눴다.
3. **둘 다 없으면 좌표→지번 폴백** — 최소한 동·번지는 보이게.
4. **오매칭 방어** — 검색 결과 중 핀 좌표 최근접 후보를 고르고 **3km 밖이면 기각**한다. 또 네이버 주소는 끝에 상호명이 붙어 오는 경우가 있어(`"백마로 487 멍스테이"`) 꼬리표를 제거했다.

**해결(2) — DB 백필: 표시용 컬럼만, 자릿수 검증으로**  
찜 목록·내 가게처럼 DB의 `stores.address`를 그대로 쓰는 화면을 위해, 검증된 실주소를 DB에도 백필했다. 좌표가 없는 가게는 **마스킹 패턴 자릿수 대조**로 검증했다 — 마스킹의 `*` 하나는 숫자 한 자리이므로 `인천타워대로***번길 **`를 정규식 `인천타워대로\d\d\d번길 \d\d`로 바꿔 후보 주소와 대조하고 시군구까지 일치해야 통과. 이 기준으로 20곳 중 16곳을 백필했고, 네이버·카카오 어디에도 근거가 없는 4곳은 마스킹을 유지했다(추측으로 채우지 않는다).

**불변식 — 정체성과 표시의 분리**  
여기서 지킨 규칙 하나: `store_key`(`"이름|마스킹 주소"`)는 찜·예약·리뷰·채팅이 전부 매달린 **정체성 키라서 절대 건드리지 않고**, 표시용 `address` 컬럼만 갱신했다. 백엔드 upsert가 기존 행의 address를 덮어쓰지 않는 것도 확인해(phone·좌표만 COALESCE 보강) 백필 값이 이후 앱 사용으로 되돌아가지 않음을 보장했다.

**배운 점**  
외부 API는 지식이나 문서가 낡을 수 있다 — 인증 실패를 "키가 잘못됐다"로 단정하지 않고 엔드포인트의 존속 자체를 의심한 것이 돌파구였다. 그리고 처음부터 정체성 키와 표시용 데이터를 분리해 둔 설계(§6) 덕분에, 주소를 통째로 갈아 끼우는 백필이 다른 도메인에 아무 파급 없이 안전했다.

### 13. 알림 — 주기 조회에서 WebSocket 이벤트와 영속 피드로

**문제**  
예약 후 자동 채팅은 남는데 홈의 종 아이콘 알림함은 비어 있거나, 알림이 늦게 보였다. 처음에는 배너 권한 문제로 볼 수 있었지만, **알림함 자체가 비어 있다는 피드백**이어서 서버 이벤트 생성·최초 조회·커서 복구부터 나눠 확인해야 했다. APNs 인증도 준비되지 않아 앱이 꺼져 있을 때의 알림까지 한 번에 해결했다고 말할 수 없었다.

**어려웠던 점과 고민**

- 채팅 자동 안내, 앱 내부 알림함, 시스템 배너는 서로 다른 표시 경로다. 하나가 동작한다고 다른 것도 동작하는 것은 아니었다.
- 초기 30초 주기 조회는 구현이 단순했지만, 앱이 열려 있어도 다음 조회까지 기다려야 했다.
- WebSocket으로 본문을 바로 보내면 빠르게 보일 수 있지만, 연결이 끊어진 동안의 이벤트와 재연결 시 중복을 별도로 복구해야 한다.
- `BGAppRefreshTask`는 서버가 정해진 간격으로 기기를 깨우는 기능이 아니었다. 이를 원격 푸시의 대체품으로 설명하지 않기로 했다.

**예전 문서에서 보존한 초기 검토 — 왜 폴링부터 시작했나**

APNs 준비 전까지 알림 기능을 미루는 방법, FCM 같은 중계 서비스를 쓰는 방법, 서버 이벤트 피드를 먼저 만드는 방법을 비교했다. 당시에는 FCM을 선택해도 iOS의 APNs 인증 준비라는 제약이 없어지지 않는다고 보고, 앱 내부 확인 경로를 먼저 구현했다.

첫 구현은 포그라운드 30초 주기 조회와 `BGAppRefreshTask`를 검토·적용한 단계였다. 이를 현재 구조로 오해하지 않도록 구분한다. 현재는 WebSocket 우선이며 백그라운드 호환 메서드가 정해진 주기로 앱을 깨우는 기능을 제공하지 않는다.

커서는 앱이 내부 필드를 해석해 다음 값을 계산하기보다 서버가 준 값을 저장했다가 그대로 돌려주는 **opaque 커서**로 다뤘다. 서버의 커서 축이 바뀌어도 앱이 각 필드의 의미에 결합되지 않게 하려는 선택이었다.

초기에는 자동 채팅 메시지를 만드는 이벤트와 예약 이벤트를 별도 축으로 나누어 중복을 막으려 했다. `INSERT INTO chat_messages` 호출 지점을 추적해 어떤 이벤트가 어느 경로에서 생기는지 확인한 과정도 있었다. 다만 **이 초기 분류 규칙을 현재의 표시 경로와 동일시하지는 않는다.** 지금은 자동 채팅을 남기면서도 알림 유형·고유 ID·이동 대상을 별도로 지정한다.

예전 문서에서 보류했던 동초 커서 경계와 취소 알림 유실은 이후 최초 복원·증분 조회 회귀의 입력으로 삼았다. 과거의 ‘현재 범위에서 보류’ 판단을 지금도 미해결이라는 설명으로 남기거나, 측정하지 않은 실사용 충돌 확률로 정당화하지 않았다.

**해결 — 빠른 신호와 복구 가능한 기록을 분리**

```text
예약·채팅·알림장 변경 성공
  → 서버가 계정별 변경 이벤트 발행
  → 앱 활성 중 WebSocket으로 변경 신호 수신
  → 인증된 영속 알림 피드 재조회
  → event_id로 중복 제거, 알림함 저장, 대상 화면 갱신
```

Cloudflare Durable Object의 WebSocket은 변경 사실을 알려주는 통로로, D1 기반 알림 피드는 끊긴 연결을 복구하는 기준으로 사용했다. 소켓이 전하는 신호만 믿지 않고 최초 진입·재연결·앱 복귀 때 피드를 읽게 했다. 클라이언트는 커서를 불투명한 값으로 보관하고, 동시 갱신 요청을 직렬화하되 처리 중 새 요청이 오면 한 번 더 조회한다.

서버 쪽에는 최초 알림 복원, 같은 시각의 여러 이벤트, 취소 이벤트 누락 같은 경계 테스트를 추가했다. 이벤트마다 고유 ID와 예약·채팅방 문맥을 붙여 같은 이벤트가 중복 표시되지 않게 했다. 자동 채팅 안내는 유지하되 알림의 종류와 이동 대상은 별도로 분류했다. 예약 접수·취소는 예약 내역, 알림장은 해당 예약의 알림장, 일반 채팅은 해당 채팅방으로 이동한다. 과거 알림을 최초 복원할 때는 배너를 조용히 처리하고 이후 새 이벤트와 구분했다.

**남겨 둔 안전망과 한계**

현재는 앱 활성 중 WebSocket을 우선 사용하고, heartbeat·재연결·주기 피드 조회로 누락을 보완한다. 호환용 백그라운드 갱신 메서드가 있다는 이유로 백그라운드 수신을 구현했다고 보지는 않는다. **앱 비활성·종료 상태의 원격 알림은 APNs 등록·서버 발송·인증과 실제 기기 검증이 남아 있다.** 포그라운드 이벤트 수신과 원격 푸시를 같은 성과로 묶지 않았다.

**별도로 겪은 문제 — 알림 델리게이트와 메인 스레드**

초기에는 알림 탭 후 화면을 조작할 때 `Call must be made on main thread` 예외가 발생했다. 당시 async 델리게이트에서 `MainActor`로 상태를 옮기는 코드만 보고 안전하다고 생각했지만, 시스템 콜백과 Objective-C 브리징 경계까지 확인해야 했다. completion-handler 기반 델리게이트로 변경하고, 콜백에서 필요한 값을 추출한 뒤 화면 상태 변경만 `MainActor`에 전달하도록 정리했다. 이는 프로젝트에서 관측한 문제와 대응 기록이지, 모든 async 델리게이트가 잘못 동작한다는 일반화는 아니다.

**예전 문서에서 보존한 진단 과정 — 스택에서 실제 콜백 찾기**

초기 예외의 스택에서 `$s16Dog_kindergarden22AppNotificationServiceC...didReceive...`처럼 표시된 mangled 심볼을 실제 `didReceive` 구현과 대조해 콜백 경로를 좁혔다. Swift 코드 안의 `await MainActor.run`만 확인하는 대신, 시스템 델리게이트에 진입하고 완료를 알리는 경계도 함께 살폈다.

프로젝트에서 선택한 형태는 다음과 같다.

```text
completion-handler 기반 동기 델리게이트 진입
  → 응답에서 이동 대상에 필요한 값 추출
  → Task { @MainActor in ... }로 화면 상태 변경 전달
  → 동기 콜백 안에서 completionHandler() 호출
```

예전 문서는 원인을 브리징 스텁의 스레드 가정으로 강하게 서술했다. 여기서는 그 내용을 당시 검토한 원인 가설로 구분하고, 관측한 예외·스택 대조·구현 변경과 그 이후의 확인을 해결 근거로 남긴다. 이 기록만으로 특정 SDK의 내부 계약 전체를 증명했다고 말하지는 않는다.

**예전 문서에서 복원한 사례 — 깔끔한 알림 묶음이 기록을 지웠다**

처음에는 같은 방의 시스템 알림 identifier를 `chat-<roomId>`로 고정했다. 방마다 알림 하나만 남겨 알림 센터가 같은 대화로 채워지지 않게 하려는 의도였다.

예전 기록에는 ‘안녕’, ‘하세요’를 받은 뒤 나중에 ‘바이’가 오면 새 알림이 같은 identifier의 이전 알림을 대체해, 아직 확인하지 못한 안내가 사라졌던 문제가 남아 있다. 기능이 설계대로 동작했더라도 사용자는 기록을 잃은 셈이었다. 코드 리뷰에서 스펙을 만족하는지 확인하는 것과, 두 계정의 실제 사용 흐름이 자연스러운지 확인하는 것은 다른 검증이었다.

초기에는 매 발행마다 UUID를 써서 방 단위 덮어쓰기를 피했다. **현재 구현은 서버 `event_id`를 시스템 알림 identifier로 사용하고, 값이 없을 때 UUID를 포함한 대체값을 사용한다.** 따라서 서로 다른 이벤트를 방 하나의 ID로 덮어쓰지 않으면서 같은 이벤트의 재전달도 구분한다. 예전의 UUID 전환 경험과 현재의 이벤트 ID 기반 설계를 모두 남겼다.

**배운 점**  
실시간 기능은 연결 속도만의 문제가 아니었다. 끊긴 동안의 기록, 중복, 최초 복원, 계정 전환, 알림을 눌렀을 때의 이동까지 하나의 사용자 흐름으로 다뤄야 했다. WebSocket은 빠른 신호를 주고, 영속 피드는 빠뜨린 상태를 복구하는 역할을 맡기는 편이 검증하기 쉬웠다.

### 14. 서울 전체 가게 데이터 정제 — 단일 키워드 대신 다중 근거로 분류

**문제**  
공공데이터 동물위탁관리업 API는 서울에만 500곳 가까운 업체를 등록해 두지만, 이 업종 코드는 유치원·호텔뿐 아니라 미용실·펫샵·분양업체·동물병원까지 뭉뚱그려 담고 있다. 지도에 전부 핀으로 꽂으면 "강아지를 맡길 곳"을 찾는 화면에 미용실과 분양업체가 섞여 나온다. 실제 서비스(유치원/데이케어/호텔) 업체만 골라내야 했는데, 공공데이터 자체에는 그걸 구분할 필드가 없었다.

**1차 시도 — store_type 필드, 확인 없이 믿을 뻔한 함정**  
공공데이터 응답에 `store_type`이라는 필드가 있어 처음엔 이걸로 구분되나 싶었다. 그런데 전체 483곳의 분포를 실제로 세어보니 414곳(86%)이 그냥 "호텔"이었다 — 미용실이든 유치원이든 등록 시 대부분 "호텔"을 골라 넣은 것으로, 실제 서비스와 무관하게 한쪽으로 쏠려 있어 구분력이 없었다. "필드가 존재한다"와 "그 필드가 신호를 담고 있다"는 다른 문제라는 걸 재확인하고 폐기했다.

**2차 시도 — 이름·주소·가격정보 텍스트 키워드 필터**  
가게명과 (이미 수집해 둔) 가격정보 텍스트에 "유치원"·"데이케어"·"호텔"·"훈련" 등이 있으면 유지, "미용"·"그루밍" 등이 있으면 배제하는 규칙 기반 필터를 만들었다. 대부분은 이걸로 걸러졌지만, 149곳이 판정 불가로 남았다 — 이름이 "멍뭉실", "청담펫츠"처럼 텍스트 신호가 아예 없는 창의적 조합이거나 가격정보를 못 가져온 곳들이었다.

이 149곳을 다시 훑으며 놓친 신호도 몇 개 더 찾았다 — 가격정보에 "1박(24시간)"·"종일" 같은 전형적 숙박 요금 패턴이 있거나, "Day care"·"Boarding"·"Kindergarten" 처럼 한글이 아닌 영문 표기를 쓰는 곳들. 이런 확실한 신호는 규칙에 추가해 5곳을 더 건졌다. 그런데 같은 과정에서 **반대 방향의 오류**도 발견했다 — "아담스펫 강아지 강남점"은 가격정보에 "분양가"·"허위분양 NO" 같은 문구가 있었다. 유치원이 아니라 강아지 **분양업체**였다. 텍스트 필터가 애초에 "관련 없는 업체를 include로 잘못 통과"시키고 있었던 것 — 규칙 기반 필터는 놓치는 쪽(false negative)만이 아니라 잘못 통과시키는 쪽(false positive)의 오류도 만든다는 걸 보여준 사례였다.

**막다른 길 — 나머지는 텍스트로 구조적으로 판별 불가능**  
남은 140여 곳은 "펫/도그/멍 + 창의적 수식어" 조합이라 이름 자체에 업종을 가를 신호가 없었다. 키워드를 아무리 정교화해도 이 지점을 넘을 수 없다는 걸 확인했다 — 필요한 건 더 정교한 규칙이 아니라, 업종을 **이미 분류해 둔 제3의 근거**였다.

**전환 — 텍스트 추론을 외부 분류 근거와 교차검증**
이름만으로 판별할 수 없는 업체는 외부 지도 서비스가 제공하는 업종 카테고리와 등록 지역을 보조 근거로 사용했다. 핵심은 특정 페이지 구조에 의존하는 수집 기법이 아니라, `업체명 일치 + 주소 권역 일치 + 업종 카테고리`를 함께 확인해 하나의 약한 신호가 전체 판정을 결정하지 않게 한 것이다. 출처와 운영 사용 권한이 확정되지 않은 상세 정보는 앱에서 숨기고, 분류 결과 역시 자동 삭제가 아니라 운영 검토 후보로만 사용하도록 분리했다.

**검증**  
이미 수동으로 업종을 확인한 표본으로 카테고리 판정의 방향을 먼저 대조한 뒤 나머지 판단 보류 업체에 같은 기준을 적용했다. 이름이 같더라도 주소 권역이 다르면 근거에서 제외하고, 일치 여부가 불분명하면 자동 확정하지 않았다.

**결과 — 93곳 배제, 21곳 확정 유지, 35곳은 판단보류로 남김**  
"반려동물미용"(68곳)·"애견용품"(9곳)·"반려동물분양"(7곳)·"동물병원"·"애견사료"·"패션"·"종합도소매" 등 명백히 다른 업종 91곳을 배제로 확정했다. 반대로 "반려동물호텔"·"애견훈련"·"반려견놀이터" 카테고리 17곳(+ 앞서 텍스트로 확정한 4곳)은 유지로 확정했다. 검색이 애매하거나(`no-confident-match`) 카테고리가 최상위값("반려동물")으로만 내려온 35곳은 **배제하지 않고 목록에 남겼다** — 자동화된 판정이라도 확신이 없으면 지우지 않는 쪽을 택했다. 지우는 건 되돌리기 어렵지만 목록에 남겨두면 언제든 재검토할 수 있다.

**뜻밖의 발견 — 공공데이터 등록명과 실제 영업명이 다르다**  
"멍토리니"·"멍멍슈퍼"·"제제네 멍치원" 세 곳은 공공데이터 상호명 자체엔 "유치원"이라는 글자가 없어 텍스트 필터를 계속 통과하지 못했는데, 네이버 플레이스에 실제로 걸린 영업명은 각각 "애견유치원 멍토리니"·"멍멍슈퍼 애견유치원"·"제제네멍치원 강아지유치원"이었다. 사업자 등록 시점의 공식 명칭과 실제 매장이 내건 영업명이 다를 수 있다는 뜻이다 — 텍스트 필터만으로는 절대 못 잡고, 카테고리 조회의 부산물로 우연히 얻은 신호였다.

**한계를 인정한 부분 — 이름이 같아도 업종이 다를 수 있다**  
"펫피"라는 업체는 조회 결과 카테고리가 "애플리케이션개발"로 나왔다. 이름 매칭 로직은 정확히 일치했지만, 실제로는 동명의 앱 개발 회사와 매칭됐을 가능성이 높다. §12에서 주소 정밀화 때 도입한 "핀 좌표 3km 이내" 검증을 이번 카테고리 조회에는 아직 붙이지 않았기 때문에 남은 구멍이다 — 이런 애매한 결과는 카테고리 값을 신뢰하지 않고 그대로 판단보류로 남겨, 틀린 근거로 성급하게 배제하지 않도록 했다.

**배운 점**  
1. 정형 데이터라고 무조건 신호가 있는 건 아니다 — `store_type` 필드처럼, 존재만 확인하지 말고 실제 분포(base rate)를 세어봐야 그 필드가 쓸모 있는지 알 수 있다.
2. 하나의 신호(텍스트 키워드)로 안 풀리는 문제는 규칙을 무한히 늘리기보다 독립적인 분류 근거와 주소 일치 검증을 추가하는 편이 효율적이었다.
3. 규칙 기반 필터의 오류는 양방향으로 온다 — 못 거르는 것(놓침)뿐 아니라 잘못 통과시키는 것(오탐)도 있다는 걸 분양업체 사례로 확인했고, 이후로는 "걸러진 목록"도 한 번은 반대 방향으로 의심해보는 습관이 생겼다.

### 15. 인증과 객체 단위 인가 — `user_id`를 믿던 API를 서버 세션 중심으로 전환

**문제**
기존 API는 앱이 보낸 `kakao_id`, URL의 `user_id`, 메시지의 `sender_id`를 그대로 신뢰했다. 정상 흐름은 동작했지만 요청 값을 바꾸면 로그인 없이 타인의 예약을 조회하거나, 다른 사람의 강아지로 예약하거나, 보호자가 사장님 작업을 호출할 수 있었다. 특히 `is_owner` 역할만 확인해서는 “사장님 계정인가?”만 알 수 있을 뿐 “이 예약이 들어온 가게의 사장님인가?”는 판별할 수 없었다.

**어려웠던 점**
인증(Authentication)과 인가(Authorization)를 한 문제로 처리하면 역할만 맞는 다른 사장님도 예약·채팅·알림장에 접근할 수 있다. 따라서 다음 세 조건을 각각 검증해야 했다.

1. 요청자가 실제로 로그인한 사용자인가
2. 요청자에게 사장님 역할이 있는가
3. 요청 대상 예약·채팅방·알림장이 요청자의 가게에 속하는가

또한 서버 배포만 먼저 하면 세션 토큰을 보내지 않는 구버전 앱의 보호 API가 전부 401이 되므로, DB 마이그레이션·Worker·iOS를 함께 전환해야 하는 배포 문제도 있었다.

**해결 — 인증 주체를 클라이언트 입력에서 서버 세션으로 이동**

- iOS가 카카오 액세스 토큰을 Worker에 전달하고, Worker가 카카오 사용자 API에 직접 조회해 신원을 검증한다.
- 검증이 끝나면 32바이트 암호학적 난수로 30일 세션 토큰을 발급한다. D1에는 원문 대신 SHA-256 해시만 저장해 DB가 노출돼도 저장값으로 바로 로그인할 수 없게 했다.
- 보호 API는 공통 미들웨어에서 `Authorization: Bearer <token>`을 검사하고, 세션에서 찾은 `user_id`와 `is_owner`를 요청 컨텍스트에 넣는다. 이후 라우트는 URL·본문의 사용자 번호를 인증 근거로 사용하지 않는다.
- iOS는 세션을 `UserDefaults`가 아닌 Keychain에 저장한다. 만료·폐기된 토큰으로 401을 받으면 Keychain과 앱 세션을 비우고 로그인 화면으로 복귀한다.
- 관리자·배치 API는 사용자 세션과 분리해 Worker Secret 기반 `X-Internal-Key`가 있어야 호출할 수 있게 했다.

**왜 JWT 대신 폐기 가능한 불투명 세션 토큰을 선택했나**
현재 규모에서는 요청마다 D1을 조회하는 비용보다 **즉시 폐기 가능성**이 더 중요했다. JWT는 별도 블랙리스트가 없으면 로그아웃 후에도 만료 전까지 유효하지만, DB 세션은 해당 행을 삭제하는 즉시 사용할 수 없다. 세션 수명·강제 로그아웃 정책을 단순하게 유지하면서 토큰 원문도 서버에 보관하지 않는 방식이다.

**해결 — 역할 확인 뒤에도 가게 소유 관계를 한 번 더 검사**
`stores.owner_id`에 맡겨멍 사용자 번호를 저장하고, 예약의 `store_id`를 따라가 해당 가게의 `owner_id`와 세션 사용자 번호를 비교한다. 공통 `reservationAccess` 함수가 고객 본인 여부와 가게 소유 계정 여부를 함께 계산한다.

```typescript
const row = await db.prepare(`
  SELECT r.user_id, r.status, s.owner_id
  FROM reservations r
  LEFT JOIN stores s ON s.store_id = r.store_id
  WHERE r.reservation_id = ?
`).bind(reservationId).first()

return {
  isCustomer: row.user_id === sessionUserId,
  isStoreOwner: row.owner_id === sessionUserId,
}
```

예약 확정·사장님 취소·알림장 작성은 `is_owner`와 `isStoreOwner`가 **모두 참**일 때만 허용한다. 채팅도 `chat_rooms.store_id → stores.owner_id`를 조인해 방의 고객 또는 해당 가게 소유 계정만 접근할 수 있게 했다. 목록 API는 애초에 `JOIN stores ... AND stores.owner_id = ?` 조건으로 다른 가게의 행이 조회되지 않도록 범위를 제한했다.

**검증 결과**
빈 로컬 D1에 전체 마이그레이션을 적용한 뒤 무인증 요청, 위조 토큰, 역할 위조, 타인 강아지·예약·채팅·알림장 접근, 다른 사장님의 예약 확정, 운영자 전용 요청함 접근 차단, 가게 승인·거절, 잘못된 예약 상태 전환, 로그아웃 토큰 재사용 등 **52개 회귀 시나리오를 모두 통과**했다. iOS Debug 빌드와 Worker 배포 전 번들 검사도 성공했다.

**현실의 가게 소유자를 어떻게 판별할 것인가**
앱이 카카오 계정만 보고 현실의 사업자등록상 대표자를 자동 판별할 수는 없다. 따라서 자동 판별을 가장하는 대신 **수동 심사 경계**를 명확히 만들었다.

1. 사장님 역할 계정이 가게를 검색해 등록 요청을 보낸다.
2. 서버는 `stores.owner_id`를 바꾸지 않고 `store_owner_applications`에 `PENDING` 요청만 저장한다.
3. 일반 계정과 사장님 계정에는 없는 운영자 권한을 서버에서 사전에 지정한 계정에만 부여한다.
4. 운영자 전용 화면에서 신청자의 닉네임·연락처·이메일·주소와 가게 정보를 확인하고, 사업자등록증 등 별도 자료와 대조한다.
5. 운영자가 승인한 경우에만 D1 batch로 `stores.owner_id=신청자 user_id`와 신청 상태·검토자·검토 시각을 함께 기록한다. 거절하면 소유권은 연결하지 않는다.

클라이언트 입력으로 운영자 권한을 얻을 수 없고, 화면을 억지로 열어도 서버가 세션의 최신 권한을 다시 검사한다. 또한 승인 전에는 `owner_id`가 비어 있으므로 기존의 객체 관계 권한 검사에서 예약·고객 정보·채팅·알림장 접근이 자연스럽게 차단된다. 한 가게에는 승인 대기 요청을 하나만 허용하고, 이미 다른 사장님에게 연결된 가게의 요청도 409로 막았다.

**현재 한계와 다음 단계**
이번 구현은 소유권을 **안전하게 승인할 수 있는 기술적 절차**를 만든 것이며, 사업자등록증 진위나 대표자 일치를 자동 검증하는 시스템은 아니다. v1.0 파일럿에서는 운영자가 신청자에게 별도로 증빙을 받아 수동 확인하고, v2에서 증빙 업로드·본인 인증·사업자 상태 조회가 필요할지 판단한다. 운영 반영 시에는 인증 마이그레이션·Worker·iOS 앱을 함께 배포하고 최소 인원의 운영자 계정에만 권한을 부여한다.

**배운 점**
- 로그인 여부만 확인하는 것은 보안의 시작일 뿐이며, 실제 서비스에서는 매 요청마다 “이 사용자가 이 객체를 다룰 수 있는가”를 검증해야 한다.
- 역할 기반 접근 제어(RBAC)만으로는 다중 가게 환경을 보호할 수 없고, `reservation → store → owner` 같은 객체 관계 기반 접근 제어가 함께 필요하다.
- 보안 변경은 코드 한 부분이 아니라 로그인 제공자, 서버 세션, DB 관계, iOS 저장소, 배포 순서, 회귀 테스트까지 하나의 흐름으로 다뤄야 했다.

### 16. xcconfig만으로는 지킬 수 없는 Secret — 앱 직접 호출을 Worker 프록시로 전환

처음에는 API 키를 Git에서 제외된 `xcconfig`로 옮기면 보안 문제가 해결된다고 생각했다. 소스 저장소 노출은 막을 수 있었지만 Release 앱의 `Info.plist`와 실행 번들에는 값이 주입되므로, 사용자가 Naver Client Secret·Kakao REST Key·공공데이터 Service Key를 추출할 수 있다는 문제가 남았다. **저장소 비공개와 앱 번들 비공개는 다른 문제**였다.

단순히 범용 검색 프록시를 만들면 내 서버가 타인의 API 호출 중계기로 악용될 수 있어, Worker는 검색어를 받지 않고 `storeKey`만 받도록 설계했다. 서버가 D1에서 가게명·주소·좌표를 찾아 공급자 요청을 구성하고, 로그인된 사용자와 `ACTIVE` 파트너 가게만 허용했다. 장소 결과는 24시간, 블로그는 15분 D1 캐시를 적용해 외부 API 호출량도 줄였다. 공급자 오류 원문과 요청 URL은 앱에 전달하거나 로그로 남기지 않았다.

iOS에서는 Naver/Kakao REST 직접 호출 코드를 제거하고 Worker 응답만 해석하도록 변경했으며, `Info.plist`와 `Create.xcconfig`에서 서버용 키 네 종류를 제거했다. Release smoke가 소스 설정과 완성된 `.app` 번들을 모두 검사해 금지 키 항목이 있으면 실패하도록 보강했다. 그 결과 빈 D1 전체 마이그레이션, Worker dry-run, API 권한 회귀 **121/121**, iOS Release 빌드와 번들 검사를 한 번의 명령으로 검증할 수 있게 됐다.

**왜 이 방법을 선택했는가**
- Secret은 난독화가 아니라 신뢰 경계 밖인 서버에 둬야 한다.
- 사용자 입력 검색어를 그대로 중계하지 않아 프록시 남용 범위를 줄인다.
- 캐시와 정규화 응답으로 비용·공급자 종속성·오류 정보 노출을 함께 낮춘다.
- 키 교체는 새 Worker Secret 등록 → 앱 전환 → 번들 검사 → 기존 키 폐기 순서로 진행해 서비스 중단을 피한다.

### 17. 다른 기기에서 비어 있던 프로필 — 로컬 저장과 계정 동기화의 차이

**문제**

마이페이지에서 이름·연락처·주소를 저장했는데, 같은 계정으로 다른 시뮬레이터에 로그인하면 빈칸으로 보였다. 같은 기기에서 로그아웃 후 다시 로그인하는 확인만으로는 기기 간 유지 여부를 검증할 수 없었다. 이메일도 같은 경로를 사용하는지 함께 확인해야 했다.

**어려웠던 점과 고민**

`UserDefaults`에 남아 있는 값은 그 기기의 캐시일 뿐이었다. 로컬 값을 항상 서버에 올리면 빈 기본값이 정상 서버 데이터를 덮을 수 있고, 서버 응답을 항상 적용하면 사용자가 방금 수정한 값을 먼저 시작한 조회가 되돌릴 수 있었다. 다른 계정으로 바뀌었을 때 이전 사용자의 값이 남는 것도 막아야 했다.

**해결**

- 프로필 저장은 인증된 서버 API에 반영하고, 로그인·세션 복원 시 서버 응답으로 네 필드를 복원했다. 로컬 저장은 재사용을 위한 사본으로 남겼다.
- 서버의 `null`도 이전 계정의 캐시를 남기라는 뜻으로 해석하지 않고, 해당 계정의 빈 값으로 교체했다.
- 조회 시작 시 사용자 ID·토큰·API 주소·프로필 revision을 캡처했다. 응답이 돌아왔을 때 신원이 같고 사용자가 더 최근 값을 저장하지 않았을 때만 적용했다.
- 저장 요청도 제출 순간의 값과 계정을 캡처해, 기다리는 동안 바뀐 화면의 입력이나 계정을 다시 읽지 않도록 했다.

**검증과 배운 점**

차가운 세션 복원, 이메일 수정·초기화, 계정 교체, 조회보다 저장이 늦게 시작되는 순서를 회귀로 확인했다. “앱을 다시 켜도 남는다”와 “같은 계정이면 다른 기기에도 남는다”는 다른 요구사항이었다. 입력 편의성을 위한 캐시와 계정 데이터의 기준을 구분한 것이 핵심이었다.

관련 구현: `UserProfile.swift`, `AuthSession.refreshProfile`, 프로필 저장 화면, `ProfileSyncTests.swift`.

### 18. 강아지 사진 — 큰 파일 업로드보다 어려웠던 크롭 결과와 접근 권한

**문제**

사진을 고르면 용량 제한에 자주 걸렸고, 원 안에서 확대·이동해 맞춘 사진이 저장 후에는 원본 비율로 보였다. 단순히 업로드 제한만 늘리거나 화면에 `Circle`을 씌우는 것으로는 두 문제를 함께 해결할 수 없었다.

**어려웠던 점과 고민**

1. 큰 원본을 그대로 디코딩하면 전송 전에 메모리 부담이 커진다.
2. 화면의 원·확대율·이동량은 미리보기 좌표이고, 저장할 픽셀 영역은 원본 이미지 좌표다.
3. R2에 올라갔다는 사실만으로 계정별 사진이 보호되지는 않는다. 예약을 받은 점주에게 필요한 읽기 권한과 반려견 소유자의 수정 권한도 달랐다.

**해결 — 파일 처리·기하 계산·권한을 나누기**

파일 기반 선택과 ImageIO 썸네일 생성을 사용해 원본 전체를 불필요하게 펼치지 않고, 방향 정보를 적용한 제한 크기 이미지를 만들었다. 현재 반려견 사진 정책은 원본 최대 50,000,000바이트, 정규화 최대 1600px·1,500,000바이트 JPEG다. 모든 크기를 무제한 허용한다고 설명하지 않았다.

크롭은 `PetPhotoCropGeometry`에서 원의 위치·지름과 이미지 확대·이동량으로 원본의 정사각형 영역을 계산하고, 저장 시 그 영역을 실제 JPEG로 렌더링하도록 바꿨다. **JPEG에 원형 투명 파일을 저장한 것이 아니라, 잘린 정사각형 픽셀을 저장하고 프로필 화면에서 원형으로 표시**한다. 미리보기와 저장 결과가 같은 영역을 가리키도록 한 것이다.

R2 버킷은 비공개로 두고 인증 API를 통해 사진을 읽는다. 서버는 사진 소유자 또는 해당 예약·승인 가게의 관계를 확인하고, 교체·삭제 권한은 소유자에게 제한한다. 앱에서도 승인된 사진 API의 origin·경로만 인증 토큰과 함께 요청하도록 제한했다.

**검증과 남은 한계**

비율·확대·이동의 경계와 렌더링 픽셀을 테스트했고, 사용자도 원형 표시와 확대·이동 저장을 확인했다. 예약 선택·완료 화면·알림장까지 같은 실제 사진을 사용하도록 연결했다. 사진 방향·기기별 제스처의 최종 사용성은 자동 기하 테스트와 별도로 확인해야 한다.

**배운 점**

원형으로 보이는 것, 선택한 영역을 저장하는 것, 저장된 파일을 누구에게 보여줄지는 각각 다른 문제였다. 스토리지를 바꾸는 것만으로 이미지 기능이 완성되지는 않았다.

### 19. 예약 확정 후 사라지던 정보 — 스냅샷과 예약 단위 기록

**문제**

사장님이 예약을 확정하면 요청 목록에서는 빠지고 알림장만 남아, 예약 당시 알레르기·요청사항·보호자 연락처를 다시 확인하기 어려웠다. 같은 고객이 같은 강아지로 여러 번 예약했을 때 기록을 어떤 단위로 묶을지도 정해야 했다.

**고민**

현재 프로필만 참조하면 나중에 연락처나 주의사항을 수정했을 때 지난 예약의 의미까지 바뀐다. 반대로 예약 당시 사진·모든 관계를 복제하면 저장과 삭제 정책이 복잡해진다. 또 사장님은 이용일로 예약을 찾고 싶지만, 알림장은 예약 전체를 이어서 보고 싶어 했다.

**해결**

- 확정 예약 상세에 **정보 / 알림장** 탭을 두어, 확정 후에도 예약 정보를 계속 확인할 수 있게 했다.
- 신규 예약은 신청 순간의 보호자·반려견 정보와 예약 화면 입력을 `booking_snapshot`에 보관했다. 스냅샷이 없는 과거 예약은 현재 정보 기준임을 구분하고, 알 수 없는 과거 값을 임의로 채우지 않았다. 사진은 기존 인증 경로를 재사용했다.
- 확정 예약 목록은 한국 이용일 기준 주간 선택·월 달력·오늘 버튼으로 찾도록 했다. 여러 날 예약은 각 이용일에 같은 예약을 표시하지만 예약이나 알림장 데이터를 복제하지 않는다.
- 알림장은 `reservation_id` 한 건의 전체 기록을 보여주고, 서버의 최초 `created_at`을 한국 시간으로 해석해 해당 게시일의 첫 글 앞에만 날짜 라벨을 넣었다. 수정일이나 예약일을 게시 날짜로 대신 사용하지 않는다.

여기서 **채팅방과 알림장의 묶음 기준은 다르다.** 채팅은 고객+가게 조합으로 이어지지만, 같은 고객·강아지·가게의 두 예약도 알림장은 예약별로 나뉜다. 보호자는 확정 예약 목록에서 각각의 기록에 접근할 수 있다.

**함께 해결한 날짜 선택 문제**

예약 달력의 “지금 보고 있는 월”과 “실제로 선택한 날짜”를 분리했다. 10월 28일이 선택된 상태로 11월을 탐색했다는 이유만으로 11월 28일이 예약일이 되면 안 되기 때문이다. 시간권 상세는 시작 시각에 요청 hours를 더해 종료를 표시하고, 해석할 수 없는 날짜는 숨기거나 추정하는 대신 ‘날짜 확인 필요’로 남겼다.

**검증과 배운 점**

자정·연말 경계, 여러 날 예약, 같은 날 여러 게시물, 첫 글·하루 전체 삭제, 상세 왕복 후 선택일 유지 등을 회귀로 확인했다. 날짜가 모두 같은 타입이라는 이유로 같은 상태나 같은 업무 개념으로 다루면 안 된다는 것을 배웠다. 현재 프로필, 예약 당시 정보, 이용일, 최초 게시일은 서로 다른 수명을 가진다.

### 20. 오래된 401과 알림장 응답 — `await` 뒤에도 같은 문맥인지 확인하기

**문제**

A 계정의 요청이 늦게 실패한 사이 B로 로그인하면, A의 401이 B의 토큰을 지울 수 있었다. 알림장도 이전 예약의 조회나 삭제 실패가 나중에 도착해 새 화면의 기록을 덮거나 삭제한 글을 되살릴 수 있었다.

**어려웠던 점**

`MainActor`는 동시에 상태를 쓰는 실행을 직렬화하지만, `await` 전후가 하나의 트랜잭션이라는 뜻은 아니었다. `Task.cancel()`도 이미 진행 중인 응답이 반드시 사라진다는 보장이 아니므로 취소 여부만 확인해서는 부족했다.

```text
A 요청 시작 → B 로그인/다른 예약 이동 → B 응답 반영 → A 응답 도착
                                           ↑ A 결과는 여기서 버려야 한다
```

**해결**

- 401 처리는 상태 코드만 보지 않고 **실제 전송한 요청의 Bearer·API origin·경로**가 현재 세션의 것인지 확인한다.
- 토큰을 비운 뒤 대기열에 있던 만료 이벤트가 처리되는 사이 새 로그인이 완료됐다면, 이전 이벤트가 새 세션을 비우지 않게 했다.
- 알림장에는 사용자·토큰·서버·예약·작성 권한 identity와 화면 활성화 세대, 조회 세대를 적용했다. 응답 반영 시점에 다시 비교한다.
- 삭제 실패 때 전체 배열 백업을 복원하던 방식을 버렸다. 서버 성공 뒤 해당 글만 제거하고, 삭제 전에 시작된 조회가 늦게 와도 확정 삭제 ID를 되살리지 않게 했다.
- 현재 권한 오류가 발생하면 비공개 목록뿐 아니라 열린 작성창·사진 갤러리도 정리한다. 일반 갱신은 작성 중인 화면을 불필요하게 다시 만들지 않는다.

**검증과 배운 점**

지연 401·서버 전환·대기 중 만료 이벤트, 예약 A→B 조회 순서, 취소를 무시한 완료, 동시 삭제·늦은 삭제 실패를 순서 제어 테스트로 확인했다. 객체나 화면이 아직 메모리에 있다는 이유만으로 그 응답을 적용해도 되는 것은 아니었다. “응답이 성공했는가”보다 먼저 “이 응답이 아직 이 화면의 것인가”를 확인해야 했다.

이미 서버가 접수한 쓰기를 화면에서 취소했다고 서버 작업까지 되돌렸다고 보지는 않는다. 화면 응답 폐기와 서버 작업 취소는 별개로 남겨 뒀다.

### 21. 채팅 전송 경합 — 오래된 응답을 버리는 것만으로 끝나지 않았다

**문제**

채팅 코드에는 `isSending` 값이 있었지만 전송 진입을 막는 검사는 없었다. 전송 실패 시 이전 글을 입력란에 무조건 복원해 기다리는 동안 쓴 다음 초안을 덮을 수 있었고, 조회 순서가 뒤집히면 최신 대화가 과거 목록으로 바뀔 수 있었다. 갱신은 메시지 개수만 비교해 같은 개수의 다른 내용도 놓쳤다.

**고민과 1차 해결**

새 서버 프로토콜부터 만들기보다 현재 API 위에서 클라이언트 상태의 소유권을 먼저 바로잡았다. 네트워크 호출을 최소한의 주입 경계로 분리해 실제 모델을 테스트하고, 방·사용자·가게·토큰·서버와 세대를 캡처했다. 전송 중 재진입은 모델에서 차단하고 버튼에도 진행 상태를 표시했다. 실패한 글은 입력이 비어 있을 때만 복원해 새 초안을 덮지 않도록 했다.

서버 메시지에는 `message_id` 기반의 안정적인 행 ID를 부여하고 ID·화자·본문을 비교했다. 개수만으로 변경을 판단하거나 조회 때마다 UUID를 다시 만들어 같은 말풍선을 새 행으로 취급하지 않게 했다. 읽음 처리도 기다린 뒤 바뀔 수 있는 현재 사용자 값이 아니라 요청 당시 사용자·방을 사용한다.

**리뷰에서 다시 발견한 문제**

처음에는 전송 전에 시작된 조회를 폐기하면 낙관적으로 추가한 새 말풍선이 사라지는 문제를 막을 수 있다고 생각했다. 그런데 **채팅방 최초 조회가 끝나기 전에 전송하면, 기존 대화까지 버려지고 새 말풍선만 남는 상황**이 독립 리뷰에서 재현됐다. 폐기 조건은 있었지만 복구 경로가 빠져 있었다.

**최종 해결**

진행 중인 조회 세대를 따로 추적해 전송이 그 조회를 무효화했으면, 전송 완료 뒤 서버의 전체 기록을 한 번 다시 읽도록 했다. 전송 중 여러 변경 신호도 후속 조회로 합쳤다. 자동 재조회가 성공했다고 전송 실패 안내까지 사라지지 않게 조회 실패와 전송 실패를 구분했다. 화면의 전송 콜백도 생성 당시 세대와 문맥을 캡처해 다른 화면의 초안을 보내지 못하게 했다.

**검증 결과와 남은 선택**

기존 모델에 대한 12개 테스트에서 25개 실패를 먼저 확인했다. 토큰 누락과 리뷰 경계를 추가한 최종 채팅 회귀는 21개가 통과했다. 별도 리뷰의 초기 조회 재현도 수정 후 통과했다. 이 21개는 전체 앱 테스트 165개에 포함되는 부분집합이며 서로 더한 숫자가 아니다.

새 초안을 작성했다가 지워 현재 비어 있다면 실패 원문을 복원하는 정책은 유지했다. 실패 글 보관함이나 자동 재전송, 서버 idempotency 키를 추가한 것은 아니며, 네트워크 단절 시 서버 접수 여부가 불명확할 수 있다는 한계도 남긴다.

**배운 점**

비동기 상태 관리는 **무효한 결과를 버리는 조건과, 유효한 전체 상태를 다시 만드는 경로**가 한 쌍이어야 했다. 검사가 많아졌다는 사실보다 사용자가 끝에 어떤 대화를 보게 되는지를 다시 확인하는 것이 중요했다.

### 22. 테스트가 멈추거나 통과해도 끝이 아니었다 — 재현과 배포 검증의 경계

**문제**

수정 후 테스트가 통과하더라도 실제 앱 번들에 고지 파일이 빠지거나 Release에서만 경고가 생길 수 있었다. 반대로 시뮬레이터가 테스트 실행 준비 단계에서 멈추면 코드의 기대 실패를 확인한 것처럼 오해할 위험이 있었다. 인증 테스트끼리 공유 Keychain을 바꾸는 경합도 있었다.

**고민**

기능 테스트·환경 문제·배포 문제를 한 줄의 ‘성공/실패’로 묶지 않기로 했다. 특히 지연 응답은 타이밍에 기대어 재현하기보다, 테스트가 응답 순서를 직접 통제하도록 해야 했다.

**해결**

- Swift async gate로 응답을 보류하고, 계정·화면 변경이나 두 번째 응답 뒤에 첫 응답을 완료시켜 문제를 재현했다. 수정 전 실패와 수정 후 통과를 같은 시나리오로 확인했다.
- 공용 Keychain과 기본 설정을 쓰는 인증·알림 테스트는 각각의 `.serialized`만으로는 서로 격리되지 않았다. 공통 직렬 부모 suite로 묶었다. 실제 Keychain 테스트에는 서명된 시뮬레이터 호스트가 필요하다는 조건도 분리했다.
- 실행 worker 준비 시간 초과는 유효한 RED로 세지 않았다. 임시 전용 시뮬레이터에서는 실제 앱 테스트를 다시 실행하고, 검사 후 그 임시 기기만 정리했다.
- 채팅의 동기 자격증명 콜백은 기능 테스트를 통과했지만 Release 경고 게이트에서 actor 격리 문제가 드러났다. 콜백의 `@MainActor` 함수 타입을 명시하고 전체 앱·Release 검사를 다시 통과시켰다. 경고 필터를 느슨하게 바꾸지 않았다.
- Worker는 잠긴 의존성, 빈 로컬 D1 마이그레이션, 인증·권한 회귀를 검사한다. 추가 13개 독립 서버 suite를 `npm test`와 CI에 연결해 첫 실패에서 중단하게 했다. 운영 확인은 데이터를 만들지 않는 별도 읽기 전용 검사로 분리했다.

**기록된 검증 범위 — 2026-11-01 기준**

| 대상 | 확인한 결과 | 이 결과가 대신하지 않는 것 |
|---|---|---|

### 23. 출처를 모르는 아이콘 — 그림 검색에서 파일 해시와 라이선스 기록까지

**문제**

호텔·뼈다귀 아이콘의 원본 출처가 기록되지 않았다. 기존 아이콘들이 Flaticon에서 왔다는 이유로 두 파일도 같은 출처라고 추정하기 쉬웠지만, 실제로 확인한 근거는 없었다.

**고민과 해결**

검색 결과의 비슷한 그림이나 제작자 이름만으로 고지를 채우지 않았다. 로컬 PNG와 후보 파일을 대조했고, 두 파일 모두 Google Noto Emoji의 특정 버전과 SHA-256까지 완전히 일치함을 확인했다. 호텔은 2021년 버전, 뼈다귀는 2025년 버전의 원본 링크로 고정했다.

- [호텔 원본](https://github.com/googlefonts/noto-emoji/blob/9481ce20ef21f0c658344417901228e73aaf3480/png/512/emoji_u1f3e8.png)
- [뼈다귀 원본](https://github.com/googlefonts/noto-emoji/blob/f3ae03f5e9b3b8516fa151f7168159ca1a3e7515/png/32/emoji_u1f9b4.png)

**출처를 찾은 뒤에도 남은 문제**

호텔 버전의 루트 LICENSE는 Apache 2.0이었지만, 뼈다귀 버전은 README의 이미지 안내와 루트 OFL 1.1 고지가 달랐다. 이를 임의로 ‘둘 중 아무 라이선스나 선택 가능’으로 해석하지 않고, 각 사용 버전의 링크·저작권·두 고지 원문과 차이 설명을 앱에 함께 보존했다. 적용 범위의 최종 권리 확인까지 자동으로 끝났다고 보지는 않았다.

**검증과 배운 점**

기존 Flaticon 출처 7개를 유지하고 두 아이콘에 Google LLC / Noto Emoji 표기를 추가했다. 앱에서 오프라인으로 전문을 열고 복사할 수 있도록 고지 파일을 동봉하고, 실제 Debug·Release 앱의 파일 해시를 검사했다. 이미지 파일 자체는 바꾸지 않았다.

기술적으로 동작하는 것과 배포할 권리가 확인된 것은 별개의 조건이었다. 아이콘 원본 확인이 공공데이터·업체 사진·App Icon의 권리까지 증명해 주지는 않으므로 각각의 미확인 항목은 출시 문서에 남겼다.

### 24. 입력이 안 되는 것처럼 보일 때 — 콘솔 경고·시뮬레이터·실기기 문제 분리

**증상과 조사**

프로필 입력 중 `The variant selector cell index number could not be found.`와 `keyboardHorizontalSizeClass may only be set for UIKBDynamicRenderFactory, changes not saved`가 출력됐다. 이후에는 프로필과 강아지 등록 화면에서 입력란을 눌러도 키보드가 나오지 않는다는 신고가 있었다. 확인 과정에서 두 번째 신고 환경이 실제 iPhone이 아니라 **Mac Simulator**임을 구분했다.

로그 문자열만으로 앱 결함이라고 단정하면 시스템 키보드 구현에 의존하는 우회 코드를 넣게 된다. 반대로 입력이 정말 막혔는데 ‘시스템 로그’라고 넘겨서도 안 됐다. 따라서 앱의 `TextField`·`Binding`·저장 동작과 소프트키보드 표시를 나누어 확인했다.

**대응과 확인 범위**

- production 입력 화면 원문을 사용한 분리 UIKit 하네스에서 프로필 이름·연락처·주소·이메일을 실제 탭하고 소프트키보드 표시와 입력을 확인했다.
- 강아지 등록6개 입력란의 탭·키보드·영문 입력, 한글 모델 값6개의 UI 표시를 확인했다. 붙여넣기 메뉴 탐색은 자동화에 실패했으므로 한글 직접 입력까지 전부 검증했다고 쓰지 않았다.
- 앱 입력 결함은 재현되지 않아 강제 키보드·언어 제한 해제 같은 추측성 수정을 하지 않았다. 키보드가 계속 숨겨지는 환경에서는 Simulator의 하드웨어 키보드 연결·소프트키보드 표시 설정을 별도로 확인하도록 남겼다. 그 설정이 원 신고의 확정 원인이었다고 단정하지는 않는다.
- 예약 화면에서는 별개의 요구에 따라 입력란 밖·서비스 선택 시 키보드를 내렸다. 이후 달력 전체에 붙인 dismiss 탭이 날짜 선택과 충돌하는 경로를 제거했다(§27).

**해결 완료와 구분한 환경 신고**

`Developer App Certificate is not trusted` 실행 실패와 ‘충전은 되지만 Xcode 기기 목록에는 안 나옴’도 전달받았다. 전자는 개발 인증서 신뢰·서명, 후자는 USB 데이터 연결·기기 인식 경로를 분리해 점검할 문제다. 다만 이 대화와 저장소에는 최종 원인·해결 확인이 없으므로 앱 코드 수정으로 해결했다고 적지 않는다. 재점검 시 오류 원문, Xcode 장치 목록, 연결 경로와 실제 재실행 결과를 남겨야 한다.

**근거:** [배포 기록3.2·3.4](DEPLOYMENT_REMAINING.md), 사용자 환경 확인 답변. 환경 신고를 자동 테스트 성공으로 대신하지 않았다.

### 25. 간헐적인 지도 BAD_ACCESS — 화면 복원과 SDK 자원 수명은 다른 문제였다

**문제**

‘코코’ 검색 후 ‘디어코코’ 상세로 들어가면 `EXC_BAD_ACCESS`와 화면 정지가 발생했지만, 앱을 다시 열면 정상 진입하는 경우도 있었다. 동시에 상세에서 뒤로 갈 때 확대했던 지도 위치가 초기화되는 문제가 있었다. 매번 재현되지 않는다는 사실은 신고를 부정하는 근거도, SDK 내부 원인을 확정하는 근거도 아니었다.

**조사와 해결**

카메라·검색·필터 등 사용자의 탐색 상태는 라우터에 보존하고, 지도 엔진 객체는 화면 수명에 맞춰 다뤘다. 임시 화면 가림에서는 `pauseEngine()` 후 다시 활성화할 수 있게 하고, SwiftUI가 컨트롤러를 실제 제거하는 `dismantleUIViewController`에서는 `tearDownMap()`으로 정리했다.

정리 시에는 중복 실행을 막고 대기 중 콜백 세대를 무효화했다. SwiftUI 콜백, 지도 이벤트 delegate, 엔진 delegate, 핀·레이어·지도 참조를 비운 뒤 엔진을 reset하고 컨테이너를 제거했다. 지연 콜백은 현재 지도 객체·가시성·해제 여부·세대가 모두 맞을 때만 반영한다. 지도가 준비되기 전 핀 갱신도 막았다. 단순히 모든 곳에 weak를 붙이는 대신, **잠깐 안 보이는 상태와 완전히 종료된 상태**를 구분한 것이다.

**검증과 남은 한계**

지도 복원, 반복 teardown, 늦은 콜백 무시, 콜백 캡처 해제, pause→재활성화를 회귀로 확인했다. 테스트의 Recording 엔진이 실제 SDK를 상속해 native 자원을 만들던 경로는 작은 엔진 protocol·resource factory로 격리했다. 기존 native 테스트도 단독으로는 통과했으므로 C++ 교착이나 특정 업체 데이터가 유일한 원인이었다고 쓰지 않는다. 원 신고 기기의 반복 검색·진입은 별도 확인 대상이다.

**근거:** `961ce47`, [지도 구현](../Dog_kindergarden/Dog_kindergarden/Views/KakaoMap/KakaoMapView.swift), [수명주기 회귀](../Dog_kindergarden/Dog_kindergardenTests/KakaoMapLifecycleTests.swift), [복원 회귀](../Dog_kindergarden/Dog_kindergardenTests/HomeMapRestorationTests.swift).

### 26. 소켓을 만들었는데도 빈 알림함 — 시작 신호·영속 기록·이동 경로를 끝까지 추적

**1. 서비스가 시작되지 않던 원인**

예약 자동 채팅은 갔지만 홈 종 아이콘의 알림함도 비어 있었다. production과 같은 AppDelegate→SceneDelegate→UIHostingController 구성에서 UIKit은 active인데 SwiftUI `scenePhase`는 background로 남는 것을 확인했다. Root가 이를 비활성으로 전달해 socket과 조회가 모두 guard에서 막혔다. 기존 테스트는 서비스에 active를 직접 넣었기 때문에 이 연결 결함을 놓쳤다.

실제 SceneDelegate의 active/resign/background를 원본 신호로 사용하고 초기 UIApplication 상태와 동기화했다. 서비스 함수만 테스트하지 않고 UIKit 콜백에서 실제 서비스 시작까지 검증한 것이 중요한 전환이었다.

**2. 연결 성공 뒤에도 과거 이벤트가 사라지던 원인**

첫 조회 이전 예약을 현재 MAX 커서에 흡수하면 알림함을 처음 여는 순간 기록이 사라졌다. 새 앱은 `bootstrap=1`로 최근100개를 복구하되 초기 배너는 억제했다. 운영자 구버전 커서는 존재하지 않는 `created_at` 대신 실제 `applied_at`을 사용해500을 수정하고, 잘못된 커서는400으로 구분했다.

취소 이벤트는 예약 ID 순서와 발생 순서가 다르다. 예약 ID snapshot 상한에 취소를 묶으면 오래된 예약의 새 취소가 누락될 수 있어 취소시각·동초 ID로 별도 진행했다. 같은 초105건 취소와 생성/취소 경쟁을 회귀로 다뤘다. 이미 과거에 삼켜진 모든 이벤트를 무조건 소급 재생하거나 기존 사용자 커서를 강제 초기화한 것은 아니다.

**3. 이벤트 누락과 잘못된 화면 이동**

- 새 가게 신청 성공 뒤 활성 운영자에게 DO 변경 신호를 보내는 빠진 경로를 보완했다. 신청 거절은 상태 전이와 신청자용 영속 이벤트를 D1 batch로 묶고 첫 거절1회만 생성했다.
- 채팅 제목은 보호자에게 가게명, 점주에게 고객명으로 정리했다. 같은 방 열람 중에는 일반 채팅 배너만 생략하고 알림함에는 읽음 상태로 남겼다. 다른 방 알림을 누르면 방별 View identity를 재생성한다.
- 예약 요청·가게 사정 취소는 달력 아이콘과 예약 내역, 알림장은 실제 강아지 이름·지정 문구·알림장 아이콘과 해당 예약 기록으로 보낸다. 채팅의 회색 안내는 그대로 유지한다.
- WebSocket만 실패한 경우에도 REST 복구 뒤 화면 갱신 신호가 나가게 하고, 확정예약·알림장 목록의 누락된 이벤트 구독도 연결했다.
- 로그인 직후 시스템 알림 권한을 바로 요청하지 않고 사용자가 마이페이지 알림 설정에서 선택할 때 요청하도록 바꿨다. 알림 권한이 거부돼도 앱 내부 피드·알림함과 OS 배너를 같은 상태로 취급하지 않는다. 같은 방 알림 억제, 권한 거부, 소켓 미연결을 각각 나누어 진단한다.

카카오 로그인 동의항목의 `talk_message`와 알림톡을 같은 기능으로 취급해 예약 안내를 옮기지는 않았다. 사용자가 전환 요청을 철회했으므로 기존 채팅 안내를 유지했다. APNs도 가입·인증 후 별도 구현이며, WebSocket·로컬 알림으로 앱 종료 상태 수신까지 해결했다고 쓰지 않는다.

**검증:** 실제 Swift URLSessionWebSocketTask↔로컬 Worker/DO에서 예약·채팅·신청·거절→피드→DTO→알림함/발행 흐름과 계정 격리를 확인했다. 예약 즉시 알림은 이후 사용자도 확인했다. 이는 모든 기기의 OS 배너나 백그라운드 수신을 검증한 결과는 아니다.

**근거:** `961ce47`, [배포 기록3.4~3.9](DEPLOYMENT_REMAINING.md), [bootstrap 회귀](../backend-cloudflare/scripts/test-notification-bootstrap.mjs), [실시간 회귀](../backend-cloudflare/scripts/test-live-notifications.mjs), [거절 회귀](../backend-cloudflare/scripts/test-owner-application-rejections.mjs).

### 27. 예약 UI 수정이 입력·날짜·저장에 영향을 주지 않게 하기

**사용자가 본 문제와 실제 수정 경계**

사진이 있어도 선택칩·완료·점주 요청·상세·알림장에 기본 이모지가 나왔고, 완료 화면 사진이 너무 위에 붙었다. 선택 표시를 바꾸는 과정에서는 카드와 원형 사진 양쪽에 테두리가 생겼다. 하단 신청 패널은 가격 안내를 가리거나 버튼 모서리·그림자를 잘라 보이게 했다. 시각 수정이라도 데이터 누락·권한·선택 상태와 연결되어 있었다.

- 선택 순간의 반려견과 제출 표시값을 snapshot으로 고정했다. 응답 대기 중 다른 강아지를 골라도 완료 화면은 실제 제출한 반려견을 보여준다.
- 요청 사진 누락은 클라이언트 장식만의 문제가 아니었다. REQUEST 사진을 null/403으로 막던 서버 정책을 확인하고, REQUEST/CONFIRMED의 실제 고객·현재 ACTIVE 점주에게만 예약별 읽기를 허용했다. 원본 사진 수정·삭제는 보호자 본인 전용을 유지했다.
- 최종 선택 스타일은 바깥 카드의 일정한2pt 주황 `strokeBorder`, 사진은48pt 원형 clip만 남겼다. 주황·초록 사각 배경과 사진 원 테두리는 제거했다. 완료 사진 상단 여백, 요약 카드·마이페이지·가게 이름 박스 모서리는 각각 요청된 범위만 조정했다.
- 하단은 고정 overlay 보정 대신 실제 높이를 확보하는 `safeAreaInset`으로 바꿨다. 한 번 올린 패널이 너무 높다는 재피드백 뒤 하단 여백을 `max(20, bottomPanelInset/2+12)`로 조정했다. inset0/21/34에서20/22.5/29pt로 이전 두 위치의 중간을 사용했다. 직전 전체117개 검증과 이 마지막 한 줄의 표현식·구문 회귀를 구분해 기록했다.

**달력·시간·주의사항**

UICalendarView의 보이는 월과 선택일을 분리하고, 날짜 전체의 키보드 dismiss 탭을 없앴다. 월을 넘긴 사실만으로 같은 일자의 다른 월 예약이 되지 않으며, 실제 날짜 선택 때만 검은 원과 Binding을 갱신한다. 자정 경과·외부 Binding 교체·늦은 갱신을 검사하고 CTA 직전에도 동기 정규화했다.

시간권은 한국 시작 날짜·시각에 요청 hours를 더해 종료를 저장·표시했다. 자정·월말·연말·윤년과 duration overflow, 잘못된 ISO offset을 회귀로 다뤘다. 과거 start=end 데이터는 hours가 있을 때만 계산하고, 알 수 없는 값을 임의 한 시간으로 채우지 않는다. 주의사항의 중복 ‘메모 원문’ 행은 제거하되 라벨 없는 과거 자유메모는 특이사항으로 보존했다.

**기기 캘린더의 별도 권한 문제**

예전 취소 시 기기 일정 삭제가 조용히 실패한 원인은 쓰기 전용 권한으로 이벤트를 다시 조회하려 했기 때문이다. Full Access 요청과 async 삭제로 바꾸고 실제 목적에 맞는 안내를 유지했다. 이후에는 예약 완료 즉시 권한을 요구하지 않고 사용자가 ‘캘린더에 추가’를 누를 때 요청하도록 바꿨다. 사장님 기기에 고객 일정이 생기지 않게 하고, 사장님 취소는 보호자가 예약 내역을 열 때 상태를 동기화한다.

### 28. 정상 요청만 성공하는 API에서 잘못된 요청도 안전하게 실패하는 API로

**문제와 대응**

인증을 추가한 뒤에도 과도하게 큰 요청, JSON 파싱 실패, 비공개 응답 캐시처럼 공통 경계가 남아 있었다. TypeScript 바디 타입은 런타임에서 외부 요청을 검증하는 장치가 아니므로 §5의 정적 타입 정리와 별도로 다뤘다.

| 위험·재현 입력 | 해결 방법 | 확인한 경계 |
|---|---|---|
| 일반 API에 과대 본문 전송 | 공통2MiB 제한, D1·외부 API 처리 전413 | 사진 바이너리 전용 경로의 별도 제한과 구분 |
| 깨진 JSON, `null`, 배열을 객체처럼 처리 | 공통 객체 파싱으로400 / `INVALID_JSON` | 예약 취소의 정상 빈 본문만 허용; 잘못된 본문을 빈 객체로 삼키지 않음 |
| 로그인·예약·채팅 응답이 캐시에 남을 위험 | 비공개 API에 `Cache-Control: private, no-store`, API에 `nosniff` | 허용된 공개 GET과 보호 응답을 구분 |
| 운영자 탈퇴·재가입 후 메뉴와 권한 소실 | 서버가 검증한 카카오 ID의 SHA-256과 `ADMIN_KAKAO_USER_ID_HASH`를 비교해 로그인 시 권한 동기화 | 지정 계정만 복구; 다른 계정의 운영자 승격 차단 |
| 일반 업체에도 실제 예약·채팅이 열림 | 서버 capability와 ACTIVE 소유 승인으로 양쪽 UI/API 차단 | 사장님 역할만 맞는 무관 계정까지 허용하지 않음 |

운영자 복구는 숫자 user_id를 하드코딩하거나 앱이 보낸 admin 플래그를 믿는 방식으로 해결하지 않았다. 설정한 identity가 로그인하면 DB 권한을 맞추고, 해당 정책 아래 다른 활성 운영자 권한도 정리한다. 공개 문서에는 운영자 원문 식별값·비밀키·실제 고객 본문을 넣지 않았다.

**검증과 배운 점**

격리된 Worker/D1에 문법·크기·권한 경계 요청을 보내고, 당시 운영 배포 후 읽기·무인증 경계와 응답 헤더를 확인했다. 운영자 재가입 회귀도 추가했다. 이 자동 복구가 실제 사업자 소유 증빙이나 모든 운영 보안 검토를 대신하지는 않는다.

**근거:** `785d7bd`, `182ea2c`, `3251351`, `a8f4430`, `bc71b40`, [서버 인증 회귀](../backend-cloudflare/scripts/test-auth-permissions.mjs). 객체 단위 인가와 세션·토큰 원문 비보관 설계는 §15·20을 함께 본다.

### 29. 삭제는 화면에서 숨기는 것으로 끝나지 않았다 — 계정·예약·D1·R2 정리

**문제**

로그아웃 후 계정 정보가 남거나, 예약/회원 행만 지우고 사진 객체·알림·스냅샷이 남으면 개인정보 수명이 서로 달라진다. 반대로 기한을 모르는 과거 데이터를 추정 삭제하면 정상 기록을 잃는다.

**해결 과정**

- 계정 전환 시 프로필·최근 본 가게 등 사용자별 상태를 초기화하고 하드코딩 `userId ?? 1` 폴백을 제거했다. 로그아웃은 라우터 스택도 비워 뒤로가기로 이전 계정 화면에 들어가지 못하게 했다.
- 회원 탈퇴는 인증된 서버 처리로 세션 폐기·관련 개인정보 삭제/익명화와 클라이언트 정리를 연결했다. 예약 스냅샷·신청 거절 이벤트·사진이 추가될 때도 같은 정리 경로를 보완했다. 새 테이블을 만들 때 읽기·쓰기뿐 아니라 탈퇴를 함께 검토했다.
- 사진 업로드 응답 유실 후 재시도는 선택 UUID의 `Idempotency-Key`로 중복을 막았다. R2와 D1을 하나의 DB 트랜잭션이라고 가정하지 않고 삭제 실패·중단 객체를 `diary_photo_deletion_queue`로 재시도한다. 알림장당 최대3장·소유 관계·비공개 인증 경로를 함께 검사했다.
- 취소 예약 보관은 최종 요구대로 **취소자와 무관하게 `canceled_at + 7일`**이다. 만료 목록 제외와15분 Cron의 D1/연결 알림장/R2 물리 정리를 나눴다. 신청일을 기준으로 지우는 초기 해석은 적용하지 않았다.
- `canceled_at`이 없는 과거 예약은 날짜를 추정하지 않았다. 사용자가 별도 승인한9건만 대상 ID와 취소 상태·NULL 조건을 동시에 제한해 삭제하고 잔여0건을 확인했다. 이를 모든 NULL 행의 상시 자동 삭제 규칙으로 일반화하지 않았다.

**검증과 한계**

보유기간 경계·D1/R2 정리·탈퇴·업로드/삭제 실패를 임시 데이터로 검증했다.9건 운영 삭제는 복구 시점과 제한 조건을 남긴 별도 승인 작업이었다. 확정 예약의 기존 보관 정책과 취소7일 정책을 혼동하지 않았으며, 정책을 코드에 구현·배포했다는 사실만으로 법정 보존 의무까지 검토 완료했다고 쓰지 않는다.

### 30. 조회 실패·외부 데이터·공유 — 보이는 값이 맞는 값인지 확인하기

**실패를 빈 결과로 바꾸던 문제**

`try?`와 빈 배열 폴백은 네트워크 장애를 ‘예약 없음’, ‘내 가게 없음’, ‘리뷰 없음’처럼 보이게 했다. 채팅·예약·찜·알림장과 내 가게/신청 조회에 로딩·성공·실패를 구분하고 재시도를 연결했다. 최초 실패에는 오류 화면, 기존 성공 데이터가 있는 갱신 실패에는 데이터를 보존한 작은 오류 안내를 사용했다. 상세 리뷰·블로그·capability·작성 자격도 별도로 실패를 표시하고 이전 가게의 지연 응답을 대상 키로 차단했다.

**외부 조회 결과가 해당 가게가 아니던 문제**

지역명만 같은 블로그가 섞여 가게명 언급 필터를 추가했다. 주소는 마스킹 원본을 표시용 상세주소로 보강하되 `store_key` 원본 정체성은 바꾸지 않았다. 찜 등에서 보강된 주소로 키를 다시 계산해 다른 가게처럼 취급하지 않도록 원본 키 override를 보존했다. 크롤링 정보는 수집됐다는 사실과 사용 권리가 확인됐다는 사실을 구분했고, 미확인 상세·사진 노출과 자동 순환 갱신은 차단했다. 필드별 provenance 스키마 제안은 이미 전부 구현된 기능으로 쓰지 않는다.

**값은 있는데 동작으로 이어지지 않던 문제**

- 파트너 상세에도 전화·위치 영역을 공통 제공하고, 없거나 마스킹된 전화번호는 잘못된 `tel:`로 연결하지 않는다.
- 공유는 이름·주소·전화 문자열만 보내던 방식에서 해당 가게 링크와 공개 랜딩·앱 진입 처리로 바꿨다. 이는 Universal Links의 모든 배포 설정이 완료됐다는 의미와 구분한다.
- ‘지도에서 보기’는 이후 외부 앱 대신 내부 지도 sheet의 단일 핀·중심·주소·닫기로 변경했다. 잘못된/없는 좌표는 안내하고 홈 지도 탐색 상태는 바꾸지 않는다.
- 사용하지 않는 채팅 `+`·스마일·설정/쿠폰 같은 죽은 동작은 완성된 기능처럼 남기지 않았다. 고객센터·사진 등록도 실제 연결이 준비된 경로로 후속 구현했다.
- 고객센터는 실제 답변 담당자가 없는 가상 가게 채팅을 그대로 서비스하지 않았다. 별도 문의 대화·메시지와 운영자 답장 API로 구현하고 본인 대화/운영자 권한을 구분했다. 활성 운영자가 없으면 문의 생성·전송을503과 재시도 안내로 막는다.
- 예약 화면의 공통 고정가격·픽업 비용은 실제 업체 가격으로 오해될 수 있어 제거했다. 가격은 업체 확인 전 확정 금액으로 계산하지 않으며 미확인 가격표도 자동 공개하지 않는다.

**근거:** `14f3729`, `7fde059`, `be46107`, `37ecde2`, `ea8f934`, `0f7403d`, `bc71b40`, `5a965d9`, `961ce47`, [데이터 감사](DATA_PROVENANCE_AUDIT.md), [가게 공유 회귀](../backend-cloudflare/scripts/test-store-share.mjs). 감사 당시 수량과 당시 외부 지도 설계는 현재 운영 상태로 재사용하지 않는다.

### 31. 개발 빌드 성공과 출시 준비 사이의 실패들

**의존성과 설치 대상**

Xcode27에서 SDK Pods가 선언한 오래된 deployment target을 보완하려고 `post_install`에서 최소값을 올렸다. 이후 프로젝트의 최소 iOS가26.2로 잘못 잡혀 설치 범위를 과도하게 제한한 것을 발견했다. iOS16 강제 빌드에서 Observation·SwiftUI API 요구를 확인한 뒤 앱·테스트·Pods를17.0으로 통일했다. 현재 값은 처음 보완 당시16.0과 구분한다.

테스트 타깃은 Kakao 모듈 검색 경로가 빠져 실행 전 빌드에 실패했다. 앱 타깃 아래 테스트 타깃에 CocoaPods 검색 경로 상속을 연결하고 `pod install`로 복구했다. 테스트 러너가 특정 Simulator 런타임에서 종료되는 문제는 앱 assertion 실패로 세지 않고 정상 부팅 런타임에서 다시 실행했다.

**검사 환경이 결과를 바꾸던 문제**

Release smoke가 개발자 `.dev.vars`를 읽으면 ‘Secret 미설정 시 안전한 실패’ 검사가 로컬 키 유무에 따라 달라졌다. 권한을 제한한 임시 환경 파일과 격리 D1을 명시해 테스트 입력을 고정했다. 마이그레이션은 기존 개발 DB가 아니라 빈 DB에도 순서대로 적용했다. root 소유 npm 환경은 sudo로 덮지 않고 새 설치 경로로 우회했고, 갱신된 의존성의 audit·Worker dry-run도 검증했다(§9).

**완성 번들까지 확인한 항목**

- Swift6 actor 격리·폐기 API·중복 로그인 URL 콜백 경고를 수정하고, 앱 소스 경고만 분리하는 Release 게이트를 추가했다. 외부 SDK 경고를 숨겨 전체 경고0이라고 표현하지 않았다.

### 32. 코드 밖의 문제 — 미추적 마이그레이션·과거 worktree·중복 문서

**문제**

운영 D1에는 적용된 마이그레이션과 수집 스크립트가 Git에는 빠진 시점이 있었다. 미사용 원본 CSV가 삭제 기록 뒤 다시 추적되기도 했다. 나중에는 `PORTFOLIO.md`·`ARCHITECTURE.md`·`FEATURES.md`가 컴퓨터에 두 개씩 보여 최신본의 위치와 GitHub 반영 여부가 혼동됐다.

**대응**

마이그레이션0014~0016과 파이프라인 스크립트를 Git에 기록하고, 실행 순서·입출력 계약을 문서화했다. 당시 중복 유틸은 `scripts/lib.mjs`로 통합했다. 재유입 CSV는 실제 실행 참조와 이전 삭제 근거를 확인한 뒤 제거했으며, 데이터 사용 권리까지 해결됐다고 쓰지 않았다.

중복 MD는 최신 main 프로젝트와 예전 detached worktree의 사본이었다. 수정 시각만 믿지 않고 Git 선후 관계·원문 차이·현재 코드의 유효성을 비교했다. 과거 포트폴리오의 빠진 진단·선택 이유는 최신본에 합치고, 나머지16개 문서는10개 동일·6개 변경을 검토했다. 유효 내용은 이미 최신본에 있어 오래된 폴링·사진 제한·보관 정책을 다시 덮지 않았다.

파일별 해시와 압축 백업을 확인한 뒤 과거 문서 사본만 삭제했다. 용도가 다른 README5개·라이선스·소스·의존성·고유 내부 기록은 유지했다. 문서 통합은 `44b018d`로 main에 commit·push했으며, **과거 worktree 자체와 Git 등록을 제거한 작업은 아직 실행하지 않았다.** 과거 작업 폴더의 삭제와 최신 main의 문서 삭제, Git 과거 이력 삭제는 서로 다른 작업이다.

백업은 임시 경로라 OS 정리 대상일 수 있고, 복원 근거로 Git 이력도 유지한다. 앞으로 worktree를 제거할 때는 남은 미커밋·미푸시·untracked/ignored 작업을 다시 확인해야 한다. 과거 사본을 정리한다는 이유로 main의 같은 이름 문서를 `git rm`하거나 이력을 강제 재작성하지 않는다.

**근거:** `21452f9`, `eaf72c2`, `59a17f5`, `6039389`, `045c0eb`, `44b018d`, [문서 대조 기록3.21](DEPLOYMENT_REMAINING.md).

### 34. 동시 요청과 데이터 무결성 — 가능성이 아니라 깨진 결과를 기준으로 수정

**출발점**

사용자는 ‘동시에10개가 들어오거나 응답이 늦을 때’를 검토하되 애매한 가능성을 억지 이슈로 만들지 말라고 요청했다. 그래서 새로운 잠금·큐·멱등성 프레임워크를 먼저 설계하지 않고, 기존 Worker/D1과 실제 Swift 모델에서 요청/응답 순서를 제어했다. HTTP가 성공했는지만 보지 않고 가게·방·예약·안내 행 수, 저장 상태, 입력 중 초안까지 확인했다.

#### 34.1 같은 가게인데10개의 가게가 생겼다

**재현:** 같은 새 `store_key`로 가게 등록 신청10개를 보냈다. 기존 `resolveStoreId`는 SELECT에서 없음을 확인하고 별도 INSERT를 했다. SELECT 결과를 실제 DB에서 읽은 뒤10개 응답의 전달만 모아 늦추자, 모든 요청이 없다고 판단해 가게10개·PENDING신청10개로 나뉘었다. 이미 존재하는 가게에 최초 신청10개를 보내면 이번에는 UNIQUE 제약이9개 요청을500으로 막았다.

**선택과 해결:** 새 테이블·서비스·메모리 락은 추가하지 않았다. 기존 `resolveStoreId` 안에서 `INSERT ... SELECT ... WHERE NOT EXISTS`로 쓰기 순간에 다시 확인하고 같은 D1 batch에서 실제 정본 ID를 읽었다. 정상적으로 이미 존재하는 가게의 빠른 조회 경로는 유지했다. claim도 INSERT 경쟁을 무시한 뒤 **본인의 실제 PENDING 행**을 다시 읽어 동일 신청을 반환한다. 다른 사람의 PENDING을 내 신청으로 돌려주지는 않는다.

본인 PENDING을 조회한 NULL 응답이 늦게 도착하는 동안 같은 사용자의 두 번째 신청이 완료되는 경우도 확인했다. 중복된 ‘다른 PENDING 조회’가 자기 신청까지 다른 신청으로 오인해 첫 요청에409를 반환했다. 이 사전 조회를 없애고 원자적 INSERT와 본인 정본 조회에 판정을 모아, 동일 신청 ID·대기1건을 유지하면서 두 요청 모두 정상 반환하게 했다. 중복 검사를 줄이는 것이 오히려 경쟁 상태를 줄인 사례였다.

추가로 ‘다른 사장님 소유권 조회 결과는 NULL로 읽혔지만 전달되는 동안 기존 신청이 승인된 경우’를 재현했다. 조회 때의 권한만 믿고 INSERT하면 이미 ACTIVE인 가게에 새 PENDING이 남았다. INSERT의 SELECT 조건에 현재 `owner_id IS NULL`을 넣어 쓰기 시점에도 확인하고, 더 이상 신청할 수 없으면409로 반환했다.

수정 후 같은 요청10개는 가게1개·신청1개를 공유하고, 먼저 승인된 가게에는 지연 신청이 남지 않았다. 기존 중복 가게를 자동 병합하거나 과거 ID를 바꾼 것은 아니며, 수동 SQL 같은 별도 쓰기 경로에 전역 UNIQUE를 새로 강제한 것도 아니다.

#### 34.2 중복은 막혔는데 정상 요청9개가 실패했다

**재현:** 채팅방은 이미 `(user_id, store_id)` UNIQUE였지만 `getOrCreateRoom`의 SELECT→INSERT 사이에서10개 요청이 경쟁하면1개만 성공하고9개가500이었다. 같은 가게의 서로 다른 예약10건도 첫 방 생성에서 막혀 예약1건만 저장됐다. UNIQUE가 DB 중복을 막았다는 사실만으로 API의 경쟁 처리가 올바른 것은 아니었다.

**해결:** 기존 함수 안에서 `ON CONFLICT(user_id, store_id) DO NOTHING` 후 같은 batch에서 정본 방을 조회했다. 기존 방을 지우거나 `REPLACE`하지 않아 메시지와 관계를 보존했다. 경쟁에서 진 요청도 정상적인 같은 방 ID를 받는다.

수정 후 첫 방 요청10개가 같은 방을 반환했고, 서로 다른 예약10건은 한 방을 공유하면서 예약10건·접수 안내10건을 모두 보존했다. **서로 다른 예약을 하나로 합친 것이 아니다.** 본문이 같다는 이유만으로 두 예약을 같은 작업이라고 추정하지 않았다.

#### 34.3 상태만 바뀌고 안내는 영원히 빠지는 중간 실패

**재현:** 예약 생성·확정·점주 취소는 예약 행을 먼저 저장하고 자동 채팅을 별도 저장했다. 안내 INSERT에 의도적 DB 실패를 주입하면 생성 API는500인데 예약만 남았다. 확정/취소는 상태가 이미 바뀌어 재시도가 ‘변경 없음’으로 끝나므로, 빠진 안내가 다시 생성되지 않았다. 예약 접수·점주 취소처럼 피드가 시스템 메시지를 사용하는 경로에서도 이 간극은 중요했다.

**해결:** 같은 D1에 있는 예약 쓰기와 안내를 `DB.batch`로 묶었다. 생성은 바로 앞 INSERT의 `last_insert_rowid()`로 연결하고, 확정/취소는 바로 앞 조건부 UPDATE의 `changes() = 1`일 때만 안내를 INSERT한다. 중간에 다른 SQL을 끼우지 않는 것이 이 연결의 불변식이다. 실패하면 두 쓰기가 함께 rollback되므로 재시도가 정상 동작한다.

확정과 점주 취소에 있던 같은 대상 JOIN·INSERT는 **공통 SQL 상수 하나**로 모았다. 문구·유형은 bind하고 권한·상태 검사는 각 기존 라우트에서 읽을 수 있게 남겼다. 함수가 함수를 다시 호출하는 새 실행 계층이나 범용 전이 엔진은 만들지 않았다. 고객 본인 취소에 점주 취소 안내를 보내지 않는 규칙도 유지했다.

수정 전에도 확정/취소의 조건부 UPDATE는 같은 요청10개에 안내1건만 만드는 검사를 통과했다. 이를 동시성 버그로 부풀리지 않고, 실제로 깨졌던 **상태와 안내 사이의 원자성**만 고쳤다. DB 밖 R2까지 한 트랜잭션이 된 것은 아니므로 사진 삭제 대기 방식은 그대로 필요하다.

#### 34.4 고객센터는 일반 채팅과 달랐던 비동기 보호

**재현:** 실제 고객센터 ViewModel에서 전송을 보류하고 새 글을 입력한 뒤 실패시키면 새 초안이 실패한 글로 덮였다. 먼저 시작한 조회를 전송 뒤 완료하면 방금 보낸 메시지가 사라졌다. 반대로 DB 저장 후 POST 응답만 늦추고 GET이 그 글을 먼저 받게 하면 같은 ID가 두 번 나타났다.

또 Root의 support 딥링크는 같은 화면에서 선택 대화 ID를 바꾸는데, 기존 View의 ID 없는 task는 처음 한 번만 configure했다. 대화 제목과 실제 기록의 문맥이 달라질 수 있는 진입 경로가 있었다. 모델에서는 A의 조회·전송을 보류한 채 B로 전환해 늦은 결과가 B에 적용되는 경계를 확인했다.

**해결:** 기존 `reloadMessages`가 load/refresh의 조회·오류·중복 진입 처리를 맡게 했다. 같은 문맥 조회는 single-flight로 실행하고, 세대가 바뀌거나 취소된 응답은 반영하지 않는다. 조회를 기다리는 동안 성공한 메시지만 ID로 보충하며, 이미 GET에 있는 POST 응답은 다시 append하지 않는다. 실패 원문은 입력란이 비어 있을 때만 복원한다.

View는 대화·사용자·역할·토큰·서버를 묶은 문맥으로 task를 재시작하고 종료 시 무효화한다. 버튼/키보드 전송은 같은 `sendMessage` 경로로 문맥을 캡처한다. 일반 채팅 모델과 완전히 합치면 방 생성·역할·읽음 규칙 차이를 다루는 옵션이 늘어나므로, 이번에는 거대 공통 모델을 만들지 않았다. 실제 네트워크 대신 응답 순서만 제어할 수 있는 최소 closure 주입과 기존 함수 재사용으로 검증 가능성을 확보했다.

#### 34.5 문제가 확인되지 않은 경계와 검증의 한계

| 검토한 상황 | 확인 결과·판정 |
|---|---|
| 같은 확정/취소10개, 확정과 고객 취소의 경쟁 | 상태 전이/중복 방지는 기존에도 정상. 고객 취소를 나중 확정이 되돌리지 않았고 안내는 최대1건이었다. |
| 반려견 사진 교체10개·PUT/DELETE 경쟁 | 격리 D1/R2의 최종 메타데이터와 객체가 일치했다. 이 재현 범위에서는 추가 결함으로 판정하지 않았다. |
| 알림장 사진 동일 멱등 키10개 | 같은 photo_id·객체1개. 추가 잠금을 넣지 않았다. |
| 다른 키로 알림장 사진10개 | 3개만 저장·나머지 거절, DB/R2 일치. 최대3장 제한이 깨졌다고 주장하지 않았다. |
| 운영자 승인/거절 경쟁, 고객센터 대화 열기10개 | 실제 DB 상태와 거절 이벤트가 일치했고 고객센터는 대화1개를 공유했다. |
| HTTP 성공 응답 자체가 네트워크에서 유실된 예약 POST의 정확히 한 번 처리 | 새 멱등 키 계약을 도입한 것이 아니다. 서로 다른 작업과 재전송을 구분할 합의 없이 본문·시간만으로 예약을 합치지 않았고, 이 보장을 이번 해결 범위로 주장하지 않는다. |

가게/방 경합은 실제 Hono 라우트와 Miniflare D1/R2/DO를 사용했다. Node에서 요청을 겹치기 위해 `cloudflare:workers`의 기반 클래스만 번들 단계에서 대체했고, DO는 원본 workerd 번들에서 실행했다. DB proxy는 실제 SELECT 값의 **전달 시점만** 보류했으며 값·권한·SQL·트랜잭션을 가짜로 만들지 않았다. 변경 후와 `ef09fa4` 원본 snapshot 양쪽에서 같은 회귀를 실행했다.

예약 원자성은 실제 Worker에 실패 트리거를 넣어 검증했고, 고객센터는 실제 Swift 모델의 응답 순서를 gate로 통제했다. 이는 운영에서 모든 interleaving을 탐색했다는 뜻이 아니다. 전체 검증 수치·실행 로그와 운영 미반영 상태는 [배포 기록3.23](DEPLOYMENT_REMAINING.md)에 남긴다. 서버가 이미 접수한 쓰기를 화면 취소가 되돌린다고 보지 않으며, 실제 두 기기·실사용 네트워크 검증도 별도로 남긴다.

**배운 점:** UNIQUE가 있다는 것, MainActor에서 실행한다는 것, 재시도할 수 있다는 것은 각각 안전성의 일부일 뿐이었다. 이번에는 새 계층을 늘리는 대신 기존 생성 함수의 쓰기 시점 확인, 같은 DB의 원자적 저장, 기존 화면 조회 함수의 문맥 소유권을 바로잡았다. 단순함은 줄 수가 아니라 지켜야 할 규칙이 한 곳에서 읽히는지로 판단했다.

**근거:** [D1 batch의 트랜잭션 계약](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), [SQLite changes의 연결·문장 의미](https://www.sqlite.org/c3ref/changes.html), `test-reservation-transitions.mjs`, `test-store-identity-concurrency.mjs`, `SupportConversationStateTests.swift`. 의도적 DB 실패 로그는 검사 입력이며 운영 장애 기록이 아니다.

## 아키텍처 결정

### iOS — SwiftUI + Observation

UIKit 대신 SwiftUI를 선택한 이유:
- `@Observable` 매크로로 보일러플레이트 없이 상태 관리 가능
- 선언형 UI로 지도·리뷰·예약 화면을 빠르게 구현
- iOS 17+ 기준으로 관찰 대상 속성과 환경 주입을 정리하기 편함. 별도 비교 벤치마크 없이 성능 우위를 수치로 주장하지는 않음

### 백엔드 — Cloudflare Workers + D1

Spring Boot 대신 Cloudflare Workers를 선택한 이유:
- 서버 관리 불필요, 글로벌 엣지 배포 자동화
- D1(SQLite)으로 마이그레이션 파일 기반 스키마 관리 가능
- 별도 서버 인스턴스 관리 부담을 줄일 수 있음. 실제 요금·무료 한도와 운영 사용량은 별도 확인 대상

### 지도 데이터 — 공공데이터 API

카카오·네이버 플레이스 대신 공공데이터 동물위탁관리업 API를 선택한 이유:
- 정부가 인허가한 업체만 등록되어 있어 신뢰도 높음
- 서울 원천 데이터를 기준으로 유치원·호텔 후보를 분류하고 운영 검토 대상을 관리하기 용이
- 외부 서비스의 상세 데이터는 출처·사용 권한이 확인된 범위에서만 보강하고, 미확인 값은 일반 업체 화면에서 숨김

## UI/UX 설계 고민

디자인 시안을 기능으로 옮기며 "정보를 어떻게 배치하고, 사용자의 마찰을 어떻게 줄일까"를 계속 고민했다.

### 강아지 카드 — 정보 밀도 조절

한 줄에 `이름 / 나이 / 성별 / 견종`을 슬래시로 나열하니 답답했다. **이름을 카드의 주인공으로 키우고**, 나이는 이름 옆에, 성별·견종은 아랫줄로 분리해 시선이 자연스럽게 흐르도록 했다. 사회성·알레르기·특이사항 같은 세부 정보는 목록에서 빼고, **카드를 탭하면 열리는 상세 시트**에서 항목별 칸으로 보여줬다 — 목록은 가볍게, 상세는 충분하게.

```
[🐶]  몽이 3살          ← 이름(강조) + 나이
      남 · 포메라니안    ← 성별 · 견종
```

### 한 카드 안의 두 동작 — 탭 영역 분리

강아지 카드에는 '상세 열기'와 '삭제(−)' 두 동작이 공존한다. 카드 본문은 `contentShape(Rectangle())`로 탭 영역을 명확히 잡아 상세 시트를 열고, 삭제 버튼은 그 바깥의 독립 버튼으로 두어 오작동(삭제하려다 상세가 열리는 등)을 막았다.

### 지도 — '전국보기'를 없애고 '보이는 만큼만'

기존엔 도(道) 단위로 전환하는 '전국보기' 모드가 있었는데, 사용자가 도 경계를 신경 써야 해서 부자연스러웠다. 지도를 움직이면(`cameraDidStopped`) **현재 화면의 위경도 범위를 계산해 그 안의 가게만** 도 경계와 무관하게 표시하도록 바꿨다. 핀이 과밀해지는 걸 막으려 화면 중심에서 가까운 순으로 개수 상한을 뒀다.

### 예약 화면 — 실제 데이터와의 마찰 줄이기

- **강아지 선택**을 실제 등록 데이터로 연결해, 고르면 나이·견종·몸무게·메모가 함께 갱신된다.
- **보호자 연락처·주소**는 서버 프로필과 로컬 사본을 통해 다음 예약에서 재사용한다. 기기 내 저장과 계정 간 동기화를 구분해 입력 마찰을 줄였다.
- 실제 업체가 등록하지 않은 공통 고정가격과 픽업 비용 계산은 제거했다. 현재는 **예약 확정 전에 업체와 서비스 범위·최종 가격을 확인해야 하며 앱에서는 결제하지 않는다**고 명확히 안내한다.

### 로딩·빈 상태·실패를 눈에 보이게

목록이 비면 안내 문구, 통신 중엔 스피너 + 버튼 비활성, 실패 시 빨간 문구로 상태를 드러냈다. 사용자가 '지금 무슨 일이 일어나는지' 알 수 있게 하는 데 신경 썼다.

### 구현한 개선과 아직 남겨 둔 개선 구분

강아지 프로필의 비공개 R2 저장·크롭, 예약 달력 선택, 확정 예약의 이용일별 탐색, 예약별 알림장 게시일 구분, 앱 활성 중 WebSocket 갱신은 구현했다. 이를 계속 ‘향후 아이디어’로 남겨 현재 상태와 혼동하지 않게 정리했다.

앞으로 검토할 UI는 지도 핀 밀집도 처리, 실패 메시지의 별도 보관·재전송 경험, 파트너 정보 직접 관리 등이다. 요구와 검증 범위를 먼저 정하고 별도 작업으로 다룬다.

---

## 향후 개선 계획과 현재 한계

- Sign in with Apple의 실제 인증 구성과 기존 카카오 계정 연결 정책 검증
- APNs 기기 등록·서버 발송·인증 준비 후 비활성/종료 상태 수신과 알림 이동을 실제 iPhone에서 검증
- 파트너가 직접 영업시간·가격·사진·편의정보를 관리하는 화면과 검수 이력 검토
- 보호자·사장님 두 기기에서 예약 → 확정/취소 → 채팅 → 알림장 → 리뷰 흐름을 Release/TestFlight로 최종 확인
- 서명 Archive·Privacy Report·App Store Connect 입력·심사 계정·이미지/데이터 권리 자료 준비

현재 자동 회귀와 로컬 Release 검증은 준비 수준을 높인 근거이며, App Store 심사 통과나 실사용 장애 부재를 의미하지 않는다. 배포가 필요한 서버 변경과 Xcode에서 새 바이너리를 실행해야 하는 앱 변경도 구분해서 안내한다.
